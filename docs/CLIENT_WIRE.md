# Договорённость между приложением на телефоне и узлом (CLIENT_WIRE)

Реализовано в `src/mobile_api.rs`, проверяется `chaos/mobiletest.py` (22 проверки на настоящих узлах).

## Как телефон попадает на узел
1. Владелец включает вход для телефона: порт в `mobile_tls.json` (`{"port": 443}`) или `YANDI_MOBILE_TLS_PORT`, перезапуск узла.
2. В настройках узла карточка «Приложение на телефоне» → «Показать QR». В QR: `YANDI-PAIR-1:<base64 JSON>`, где JSON — `{host, port, pairing_code, tls_fingerprint, tls:true}` (приложение понимает и старый открытый JSON).
   Код — 6 цифр, один раз, живёт 5 минут; 5 неверных попыток сжигают его.
3. Приложение проверяет сертификат узла по отпечатку из QR (sha256 от DER), меняет код на токен (`POST /mobile/pair`). Узел хранит только хэш токена
   (`mobile_devices.json` в папке данных, права 0600). Устройств не больше 16: при сопряжении 17-го вытесняется дольше всех молчавшее, и это то же «забыть устройство» (его группы, почта и открытые сокеты убираются).

Один и тот же порт и сертификат обслуживают: прокси для телефона (первый байт 0x05), этот API (запрос `/mobile/...`) и сайт-маскировку (остальное).

## Запросы (токен: `Authorization: Bearer ...`, в том числе для сокета; в адресе токен не принимается)
| Запрос | Ответ |
|---|---|
| `POST /mobile/pair` `{pairing_code, device_name}` | `{token}` |
| `GET /mobile/info` | `{node_id (64 hex), name, version, device_id, online}`; `device_id` — 64-значный транспортный номер этого телефона (адрес в E4), не Ed25519 |
| `GET /mobile/contacts` | `{contacts:[{peer_id, display_name, online, is_manual, last_activity_ms?}]}`; `peer_id` полный, если собеседник сейчас известен узлу, иначе короткий; в списке всегда есть сам компьютер и другие телефоны владельца (`last_activity_ms` — у них) |
| `GET /mobile/chat/{peer}?limit=` | `{messages:[{id, from_peer_id, text, ts_ms}]}`, `limit` 1–500 (по умолчанию 50); `peer` — полный или короткий. Для другого телефона владельца — всегда пусто: переписка между телефонами хранится только на телефонах |
| `POST /mobile/chat/{peer}` `{text}` | обычному собеседнику — `{id, ts_ms}`; другому телефону владельца — `{ok:true}` (текст кладётся в его очередь как есть). Зашифрованный E4 приложение шлёт кадром сокета `0x30` |
| `GET /mobile/inbox?after=&limit=` | `{messages:[{id (=время, мс), from_peer_id, payload_b64, ts_ms}]}`, по возрастанию, номера больше `after`, `limit` 1–1000 (по умолчанию 200). Приложение листает страницами по 1000 (`after` = последний номер страницы), поэтому письма, которые оно не может принять, не загораживают новые. Почта от телефонов и компьютера — вся неподтверждённая; старые входящие от других узлов — новее курсора подтверждения. Параметр `since` не используется |
| `POST /mobile/inbox/ack` `{ids}` | подтверждение: из очереди удаляются **ровно** перечисленные письма (неподтверждённое старое — не расшифровалось, нет ключа, старый формат — остаётся); курсор для старых входящих от узлов — по наибольшему номеру |
| `GET /mobile/proxy/info` | `{running, host, port, upstream}` |
| `GET /mobile/pubkey/{peer}` | `{x25519_pub, ed25519_pub, signature}` для телефона владельца или самого узла; у обычных собеседников 404 |
| `POST /mobile/pubkeys` `{ed25519_pub, x25519_pub, signature}` | телефон регистрирует подписанную связку ключей |
| `POST /mobile/files` `{to_peer_id, file_name, file_size, total_chunks}` | `{transfer_id, chunk_max}` — начать передачу другому своему устройству или самому компьютеру (см. «Файлы между телефонами»); `413` — пустой/слишком большой файл или кусков, `400` — неверное разбиение или получатель, `507` — нет места, `429` — 20 незавершённых |
| `PUT /mobile/files/{id}/chunk/{n}` (тело — байты) | залить кусок; повтор безопасен; `413` — куски вместе больше объявленного размера + 28 байт на кусок |
| `POST /mobile/files/{id}/done` | `200`, если все куски на месте, иначе `409 {missing:[...]}` |
| `GET /mobile/files/{id}/status` | `{done, total_chunks, file_size, have:[...]}` — для докачки |
| `GET /mobile/files` | `{files:[{id, from_peer_id, file_name, file_size, total_chunks, created_ms}]}` — готовые файлы для этого устройства |
| `GET /mobile/files/{id}/chunk/{n}` | байты куска (получатель или отправитель, когда передача завершена) |
| `DELETE /mobile/files/{id}` | получатель после скачивания или отправитель при отмене; просроченная — `404` (её уже нет) |
| `GET /mobile/turn` | `{host, port, username, credential, ttl}` — временные данные сервера звонков, `404`, если он не настроен |
| `GET /mobile/ws` | сокет сообщений; когда устройство забывают (вручную или вытеснением), его открытые сокеты закрываются сразу |

**Ошибки тела запроса.** Обычные JSON-ручки (axum): неверный синтаксис — `400`, неверный тип поля — `422`, без `Content-Type: application/json` — `415`, тело больше 2 МБ — `413`. Две ручки с необязательным телом (`POST /mobile/groups/{id}/invite` и `/request`): пустое тело — значения по умолчанию, неверный JSON или тип — `400`.

## Сокет (двоичные кадры)
- `0x01` ping ↔ `0x02` pong.
- Сигнал звонка: телефон → узел `0x31` `[0x31][32 кому][4 длина LE][байты]`, узел → телефон `0x13` `[0x13][32 от кого][8 время мс LE][4 длина LE][байты]`. Доставляется только если адресат на связи и нигде не хранится; если его нет на связи, отправитель получает `0x14` `[0x14][32 номер]`. До 32 КБ, адресат — другое устройство владельца или сам компьютер (звонок на компьютер принимается, только пока открыта страница чата; иначе — `0x14`).
- Узел → телефон `0x10`: `[0x10][32 от кого][8 время мс LE][4 длина LE][текст]`.
- Телефон → узел `0x30`: `[0x30][32 кому][4 длина LE][текст]`.

## Шифрование
Телефон↔узел: TLS с проверкой отпечатка. Между спаренными телефонами и в чате с самим ПК — аутентифицированный E4 (описан ниже). Узел↔узел использует свой отдельный транспорт чата. Если проверенная связка получателя недоступна, Flutter не отправляет сообщение: plaintext fallback отсутствует.

## Известные границы
- Контакт, которого узел сейчас не знает, виден с коротким идентификатором, писать ему через сокет нельзя (кадр требует 32 байта) — через `POST /mobile/chat/{короткий}` тоже, пока он не появился в сети.
- Группы — см. «Группы» ниже (узел, приложение и компьютер как участник — готовы).
- Телефон за NAT до компьютера за NAT не достучится: нужен компьютер с доступным адресом (белый IP или проброшенный порт) или цепочка через ретранслятор.


## Два телефона через один компьютер
- Каждый спаренный телефон — собеседник для остальных телефонов владельца: 64-значный номер (`device_id`, из `/mobile/info`), имя с 📱 в списке контактов, «в сети» — пока открыт его сокет. Изменения «в сети» приходят кадром `0x12`: `[0x12][32 номер][1 байт: 1 в сети / 0 нет]`.
- Сообщение другому телефону: тот же кадр `0x30` (или `POST /mobile/chat/{номер}`). Узел кладёт байты в очередь получателя (`mobile_mail.json`, права 0600) и сразу пересылает кадром `0x10`, если получатель на связи. Очередь чистится подтверждением (`inbox/ack`), как и обычные входящие.
- Между телефонами узел байты не расшифровывает: приложение берёт подписанную связку из `/mobile/pubkey/{номер}`, закрепляет Ed25519 и шифрует E4. В переписке с самим ПК узел — конечная точка и расшифровывает для своего UI.
- Номер входящего (`id`) — его время в миллисекундах (одинаково в `inbox` и в кадре `0x10`), поэтому приложение не показывает одно сообщение дважды.

## Выход телефона в интернет
- Телефон открывает TLS до компьютера и просит `CONNECT хост:порт HTTP/1.1` с `Proxy-Authorization: Bearer <токен устройства>` (Basic: пароль = токен). Ответ `200` — дальше байты как есть; `407` — нет или чужой токен; `403` — цель закрыта (этот компьютер, домашняя сеть); `502` — не соединилось; `503` — больше 256 одновременных.
- Узел соединяется правилами выхода (`exit_policy::connect_public_for`): если у владельца включены внешние прокси (настройки узла) — только через них, имя цели передаётся прокси как есть.
- Внешних прокси может быть несколько (`upstream_proxy.json`, страница настроек узла). За каждым устройством закрепляется один прокси (все его соединения выходят с одного адреса); новое устройство получает наименее загруженный прокси, на котором есть место (по умолчанию до 5 устройств, предел общий и на каждый прокси отдельно; мягкий лимит сажает лишнее устройство на самый свободный, строгий отказывает: `502`). Не отвечающий прокси исключается на 10 секунд, дальше вдвое дольше, до 5 минут; его устройства переезжают на живые, а соединение, на котором прокси подвёл, повторяется на другом (до трёх попыток). Отказ самой цели прокси не штрафует. Если мертвы все, пробуется тот, у кого пауза кончается раньше; прямого выхода в обход прокси нет. Закрепление забывается после 30 минут молчания устройства.
- В приложении: небольшой прокси на самом телефоне (`127.0.0.1:10808`, понимает HTTP CONNECT, обычный HTTP и SOCKS5) + системный режим VPN без маршрутов, который объявляет этот прокси системе (Android 10+). Приложения, не уважающие системный прокси, и UDP/QUIC этим путём не идут.


### Блоки P2P-туннелей SOCKS5 и HTTP CONNECT (v1)

Между узлами данные туннеля передаются внутри YTP train или пакета BatchedWagon; прямой путь SOCKS5 (`PacketType::Socks5TunnelData = 0x52`) содержит тот же блок после внешнего байта типа. Это отдельный протокол от CONNECT телефона до компьютера, описанного выше. Оба типа используют один заголовок длиной 23 байта, но разные первые байты. Все многобайтовые числа — unsigned, big-endian.

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 1 | magic/type: `0xC8` SOCKS5, `0xC9` HTTP CONNECT |
| 1 | 1 | `version:u8 = 1` |
| 2 | 8 | `tunnel_id:u64` |
| 10 | 8 | `byte_offset:u64` — абсолютное смещение в этом направлении |
| 18 | 1 | `close:u8` — только 0 или 1 |
| 19 | 4 | `data_len:u32` |
| 23 | `data_len` | данные приложения |

Смещения начинаются с 0 независимо для каждого направления. Блок `close=1` всегда пустой и несёт итоговое смещение; закрытие ждёт всех предыдущих байтов. Общая длина должна быть ровно `23 + data_len`; обрезанный заголовок/payload, лишние байты, неверный close и переполнение `byte_offset + data_len` отвергаются. SOCKS5-парсер не принимает HTTP CONNECT и наоборот.

Получатель проверяет тип, затем версию до чтения длины, копирования payload и обращения к состоянию туннеля. Неизвестная версия (включая 0 и 2) отбрасывается с предупреждением в журнале и увеличением `tunnel_version_rejected` (`version_rejected` в `[STREAM-STATS]`); пакет не попадает в другие парсеры диспетчера и не закрывает существующие туннели. Невалидный v1 увеличивает `tunnel_stream_invalid`. Проверка происходит после обычной сборки train/распаковки batch, без дополнительных ресурсов туннеля для отвергнутого блока.

Offset обязателен: capability `STREAM_OFFSET`, выбор по peer table, JSON-блоки туннеля, SOCKS `[D7]`, прежний `[D8]` с FF marker и HTTP bincode/`YANDISO2` больше не поддерживаются. Запросы и ответы установки соединения сохраняют свои действующие форматы.

Буфер перестановки ограничен числом блоков и байтами; дубликаты и перекрытия не дублируют TCP-байты. `YANDI_RX_WORKERS>1` допускается без предупреждения UNSAFE. Потеря обеих полных копий блока оставляет дыру: по таймауту закрывается только этот поток, байты после дыры не выдаются. ACK/NACK отсутствуют, число полных копий остаётся не меньше двух.

#### Окно получателя (регулятор скорости), флаг `2` в поле `close`

Получатель потока сообщает отправителю, сколько байт уже выдано в его TCP и сколько он готов принять. Это **не подтверждение доставки отдельных блоков и не повтор**: значения только растут (меньшее окно игнорируется), потеря сообщения перекрывается следующим.

| Поле | Значение |
|---|---|
| magic/type, `version`, `tunnel_id` | как в блоке данных |
| `byte_offset` (смещение 10) | `consumed` — сколько байт входящего потока получатель уже записал в TCP |
| `close` (смещение 18) | `2` |
| `data_len` | ровно `4` |
| данные | `window:u32` — сколько ещё готов принять сверх `consumed` |

Отправитель не читает следующий блок из своего TCP-источника, пока `byte_offset + len > consumed + window`; до первого окна действует начальный запас 512 КиБ. Получатель шлёт окно при продвижении выдачи (каждые 64 КиБ либо через 100 мс) и повторяет последнее значение раз в секунду. Если окно не приходило вовсе за 1 с, регулятор для этого туннеля отключается; если окна пропали после начала (дольше `YANDI_TUNNEL_STALL_MS`, 30 с), поток закрывается с ошибкой. Блок окна не принимается как данные и не создаёт состояния туннеля.

## Файлы между телефонами
- Отправитель шифрует каждый кусок сам (файлы до 5 МБ — куски по 256 КБ по одному, от 5 МБ — по 1 МБ, до 4 параллельно; на проводе кусок не больше 1 МБ + 1 КБ): AES-256-GCM, ключ на файл, случайное число 12 байт в начале куска, метка 16 байт в конце; в проверяемые данные входят номер передачи, номер куска и их число (`yandi-file:v1|<id>|<n>|<всего>`), поэтому узел не может переставить, подменить или обрезать куски незаметно.
- Ключ, настоящее имя, размер, число кусков, тип и sha256 открытого файла уходят получателю обычным зашифрованным сообщением (`\u0001yandi-file:` и JSON). Узлу достаются только безликая подпись, размер, число кусков, кто кому и когда.
- Узел хранит куски на диске (`mobile_files/<id>/`), пока получатель не заберёт файл: до 7 дней (недокачанное — сутки), срок считается от начала передачи и проверяется при каждом обращении, плюс уборка раз в 10 минут. Лимиты: файл до 1 ГБ, до 4096 кусков, всего 4 ГБ на узле (каждая передача, в том числе незавершённая, резервирует размер + 28 байт на кусок), до 20 незавершённых передач на отправителя (у компьютера тот же лимит). Получатель после скачивания сверяет размер и sha256 и удаляет передачу с узла.

## Квитанции файлов компьютер ↔ телефон

- Телефон → компьютер: после проверки размера/sha256, сохранения файла и сообщения узел шлёт зашифрованный `\u0001yandi-rcpt:{"kind":"delivered","ids":["file_<tid>"]}`. При открытии истории на странице — `read` по тому же ID. При ошибке приёма успешная квитанция не отправляется.
- Компьютер → телефон: предложение `\u0001yandi-file:{...}` вложено в `\u0001yandi-msg:{"v":1,"cmid":"<полный msg_id hex>","text":"<предложение>"}` и затем шифруется E4. Приложение распаковывает конверт до разбора `FileOffer`, отправляет `delivered` при сохранении предложения и `read` при открытии чата. Эти квитанции относятся к сообщению с предложением; скачивание файла — отдельное действие.
- Файловый v1 и кадры WebSocket не менялись; полезная нагрузка сообщений обновлена до E4. Kotlin-сервис не расшифровывает payload и показывает общее уведомление; поля E4 обрабатывает только Dart.

## Аутентифицированный конверт E4 (ПК и телефоны)

Заголовок 134 байта: `[E4][kind:1][from:32][to:32][random_id:16][timestamp_ms:u64 BE][ephemeral_x25519:32][nonce:12]`. Kind 1 — почта/чат/квитанции/предложения файлов; 2 — живые сигналы. From/to — транспортные 32-байтовые ID, у телефона **device_id из /mobile/info**, не hex Ed25519.

После заголовка: AES-256-GCM ciphertext+tag16, затем Ed25519 signature64. AAD = `YANDI-E2E-E4\0` + весь заголовок. Ключ AES = HKDF-SHA256(shared X25519, salt=SHA256(AAD), info=`YANDI-E2E-E4-KEY`, len=32). Нулевой DH запрещён. Подпись над `YANDI-E2E-E4-SIGN\0` + заголовок + ciphertext/tag. Получатель сначала сверяет ожидаемые адреса и kind, свежесть и подпись по закреплённому Ed25519; после AEAD/UTF-8 атомарно сохраняет from+to+random_id в дисковый ledger, до передачи текста дальше.

Срок 30 суток от подписанного времени, допустимое опережение часов 5 минут. Истёкшие ID удаляются только когда соответствующие конверты уже недопустимы; свежие ID не вытесняются. Лимит 100000, повреждение/ошибка записи/переполнение — отказ, без сброса защиты. Ledger общий для сокета/inbox, сохраняется при reconnect/restart. Откат часов/данных ОС и удаление ledger владельцем/root не входят в гарантию. Возможен отказ доставки при аварии после записи replay, но до сохранения сообщения: нужна будущая общая транзакция с историей.

Связка проверяется Ed25519 и закрепляется TOFU в secure storage телефона. Изменение Ed — отказ и предупреждение; X25519 можно обновить под прежней подписью. Отпечатки SHA-256 Ed доступны в чате для независимого сравнения. Первое TOFU не доказывает личность против злонамеренного первого ретранслятора. ПК не принимает смену Ed по тому же bearer-token (409); смена identity требует нового сопряжения. Подтверждение регистрации выдаётся после успешной постоянной записи.

Обновление несовместимо с E2/E3: fallback запрещён. До выпуска обновить одновременно узел и все приложения. Старые E2/E3 сообщения в inbox новый клиент не подтверждает и не удаляет (подтверждение удаляет только перечисленные письма, поэтому они не стираются и подтверждением более новых); требуется отдельное согласованное решение о переносе/повторной отправке; срок хранения почты — 30 суток. Готовые скачанные файлы/локальная история не меняются. Сетевой прогон и проверка на реальных устройствах обязательны до release.
- Стенд для Claude: `YANDI_TEST_FILE_RECEIPTS=1 python3 chaos/mobiletest.py` с установленным Python `cryptography`. Включает обе стороны, скачивание/расшифровку и запрет понижения `Read` обратно в `Delivered`.

## Звонки и видеозвонки
- Звук и видео идут по WebRTC и шифруются между самими телефонами (DTLS-SRTP). Описания сеанса и кандидаты едут «живыми» сигналами (`0x31`/`0x13`), зашифрованными телефоном для телефона (`\u0001yandi-call:` и JSON `{v:1, t, cid, video?, ts, sdp?, cand?}`: `t` — `invite`, `accept`, `reject`, `busy`, `hangup`, `offer`, `answer`, `ice`; `cid` — строка 8–64 знака, `ts` — целое время в мс, `video` — bool, `cand` — `{candidate: строка, sdpMid?: строка, sdpMLineIndex?: целое}`). Сигнал другой версии, с неверными типами или старше 90 секунд игнорируется — одинаково в приложении и на странице узла. Сигнал от устройства, которое заблокировали или забыли, пока он ждал в очереди, страница не получает.
- Телефоны в разных сетях соединяются через сервер звонков (coturn на компьютере владельца). Настраивается один раз: `sudo bash scripts/setup-turn.sh <внешний адрес>` (порт 3478 TCP/UDP и релейные UDP 50000–50199, схема временных паролей «REST API»: имя — срок и метка, пароль — HMAC-SHA1 от имени с общим секретом, который лежит только в `/etc/turnserver.conf` и `turn.json` узла). Сервер видит только зашифрованные пакеты и кто с кем соединён.
- Доверие: сигналы — обычные конверты E4, подписанные закреплённым Ed25519 отправителя, поэтому после закрепления ключа (TOFU) ретранслятор не может незаметно подделать или подменить отпечаток DTLS. Граница — первое закрепление (злонамеренный узел в момент первого обмена ключами) и взлом самого телефона.

## Группы
Реализовано в `src/mobile_groups.rs`, проверяется `chaos/grouptest.py`. Сервер группы — узел владельца; содержимое шифруют телефоны, узел его не читает.

- **Создать** группу может телефон (`POST /mobile/groups {name, topic, about?, kind: invite|open}`, до 10 групп на устройство): он становится владельцем, ключ группы и права раздаёт он. **Удалить** группу целиком можно только на странице «Группы» (`/groups`, вкладка «Управление узла»), с повторным вводом пароля узла (`POST /api/mobile/groups/{id}/delete {password}`, неверные попытки считаются как при входе). Пароль узла не даёт прав внутри группы: модерацией, участниками, приглашениями и владельцем компьютер управляет только как обычный участник со своей ролью (см. «Группы на компьютере»); назначить телефон владельцем или создать группу от имени телефона со страницы узла нельзя.
- **Типы** (их два): `invite` — «по приглашению»: вступают по коду `XXXX-XXXX-XXXX` (выдают владелец группы и модераторы; узел хранит только хэш, срок по умолчанию сутки, число использований 1–50) либо попросив приглашение; `open` — «открытая»: вступают сразу. Старый тип `closed` в данных читается как `invite`; при создании не принимается. «Для всех» (вне узла) нет.
- **Тематика и описание:** у новой группы тематика обязательна (короткая метка до 40 знаков, нужна для каталога и будущих фильтров), описание необязательно (до 300 знаков); пустые поля в карточке не показываются.
- **Псевдонимы:** в группе участник — случайный псевдоним этой группы («Тихий Лис-42»). Номера устройств в данных групп нет: участник записан хэшем `sha256("yandi-group-member:" группа ":" номер устройства)`, у каждой группы свой. Имя, которое человек называет при вступлении, он пишет зашифрованной записью в журнал.
- **Ключ группы** создаёт телефон-владелец. Каждый участник публикует свой открытый ключ для группы (x25519, `member_pub`), владелец запечатывает ключ группы каждому и кладёт конверты на узел (`POST keys`), участник забирает свой (`GET keys`). Поколение ключа (`epoch`) растёт при смене; после выхода, изгнания или запрета участника узел ставит владельцу `rekey_needed`. Узел видит конверты как непрозрачные байты. Доверие то же, что и для ключей телефонов: подменить `member_pub` может только сам узел (см. аудит #11).
- **Повторы:** каждая запись несёт внутри шифртекста случайный номер `i`; повтор того же шифртекста под новым `seq` получатель отбрасывает.
- **Журнал** — только дописывание: запись `{seq, ts, from (псевдоним), epoch, payload_b64}`, до 65 792 байт шифртекста (64 КБ + 256 байт запаса). Телефон забирает «всё после N» (`GET log?after=N`, до 500 записей / 4 МБ за раз). На диске журнал группы не больше 32 МБ: старое уходит, номера сохраняются (`first_seq` растёт).
- **Намёк** в сокете: `0x15` `[0x15][16 номер группы][1 что][8 seq LE]`, что: `1` новая или стёртая запись, `2` ключи, `3` состав/настройки/роли, `4` группа удалена. Содержимого в намёке нет, приходит участникам; исключённому (kick/ban) и участникам удалённой группы — последний намёк, чтобы приложение убрало группу.
- **Роли и права:** *владелец* (один) — всё; *админ* — настройки группы, правила, роли «модератор/участник», действия модератора, не трогает владельца и других админов; *модератор* — `mute`/`unmute`, `kick`, `ban`/`unban` (запрещённый не вернётся ни по коду, ни в открытую), `delete_entry` (байты записи стираются, номер остаётся с `deleted:true`), приглашения, просьбы; трогает только рядовых; *участник* — читает и пишет. Роли назначаются действиями `make_admin` (только владелец), `promote` (→ модератор) и `demote` (→ участник) (владелец и админ). Правила группы принимаются клиентами от тех, кто по текущему списку узла владелец или админ (роль проверяется при применении, не при выпуске правила). Всё пишется в журнал модерации (до 1000 записей, видят участники). Запрет ссылок/медиа — дело приложения.
- Устройство, которое узел забыл, выпадает из всех групп. Владелец группы выйти не может — сначала передаёт владение (`POST /mobile/groups/{id}/owner`, на компьютере — `/api/groups/{id}/transfer`).
- **Пределы узла:** 64 группы, 256 участников в группе, 64 хранимых поколения ключа, конверт до 1024 байт, 32 действующих приглашения, 20 просьб, 5000 событий стирания, причина до 200 знаков, имя до 64; срок приглашения 1 минута – 30 суток, использований 1–50. Слишком длинные строки обрезаются.
- **Пометки в ленте (локальные, не поля протокола):** запись, не прошедшая расшифровку или с полями не тех типов, показывается как `{op:"bad"}` («повреждено»); запись поколения ниже `first_epoch`, ключа которого у клиента нет, — `{op:"lost"}` («ключ удалён с узла»). Курсор идёт дальше; если ключ у клиента есть, запись читается.

**Файлы групп** (`src/mobile_group_files.rs`): узел хранит только шифртекст кусков (ключ файла лежит внутри зашифрованной записи журнала, поэтому узел не знает ни имени, ни содержимого). Скачать — любой участник (не выгнанный); залить — не заглушённый; стереть — залившего, модератор, владелец группы. Удалили группу — удалились и файлы. ## Аватарки
Служебные E2E-конверты (внутри обычного зашифрованного сообщения E4, kind=1; узел видит только шифртекст):
- `\u0001yandi-avh:{"h":"<sha256 hex>"}` — «моя картинка сейчас такая»; пустой `h` — картинки нет/убрана;
- `\u0001yandi-avq:{"h":"<hex>"}` — «пришли картинку с этим хэшем»;
- `\u0001yandi-ava:{"h":"<hex>","png":"<base64>"}` — картинка.

Правила: PNG не больше 40 КБ (вместе с base64 и шифрованием это укладывается в предел одного сообщения узла, 64 КБ), собирается заново из пикселей (центральный квадрат ≤128×128), поэтому EXIF/GPS/время/модель телефона/XMP/эскизы не переносятся. Хэш — SHA-256 байт PNG: одинаковые картинки у разных людей хранятся одним файлом, а привязка «контакт → хэш» у каждого своя (контакты не путаются). Картинку принимает только сохранённый контакт, не заблокированный и не сам узел; принимается лишь запрошенная, с совпавшим хэшем и читаемая декодером; свою отдаёт только по запросу с её хэшем. Хэш объявляется контакту при его появлении в сети (раз за сеанс) и раз в 6 часов. Узел неизвестные служебные конверты (`\u0001yandi-…`), в том числе аватарки, молча отбрасывает (`Envelope::Ignored`), чтобы они не показывались на странице чата. Аватарки ПК (профиль страницы узла) в этом протоколе пока не участвуют.

## Группы на компьютере (узел как участник)
Реализовано в `src/group_client.rs`, проверяется `chaos/pcgroups.py` (телефон-эмулятор с настоящей криптографией) и контрольными векторами из приложения (`tests/data/group_vector.json`, сгенерированы `mobile/yandi_mobile/test/gen_group_vectors_test.dart`). Для групп компьютер — такое же устройство, как телефон: номер участника — хэш от номера узла и группы, свой ключ x25519 на каждую группу, вступает по приглашению или просьбе, создаёт группы и владеет ими. Содержимое расшифровывается только в группах, где узел состоит сам. Формат шифрования байт-в-байт как в приложении (`group_crypto.dart`). На диске (`groups_pc/`, права 0600/0700) всё закрыто AES-256-GCM-ключом из мастер-ключа узла: состояние (закрытые ключи участника, ключи групп, закреплённые ключи владельцев) и расшифрованная лента; без мастер-ключа каталог ничего не даёт. Страница — `/groups` (вкладка «Мои группы»: чат с эмодзи и скрепкой; файлы до 200 МБ шифруются и режутся узлом в формате приложения, `POST /api/groups/{id}/upload?name=` — тело запроса сам файл; `GET /api/groups/{id}/file/{seq}` — расшифровка и проверка sha256 в узле, отдача как чужого вложения: безопасные картинки/звук/видео на месте, остальное на скачивание, `nosniff` и `sandbox`), ручки `/api/groups...` (только вошедшему в админку): `create {name, topic, about?, kind: invite|open}`, `join`, `request`, `messages`, `send`, `rules`, `leave`, `forget`, `info` (в том числе журнал модерации своей группы), `mod`, `settings`, `transfer`, `upload`, `file/{seq}`, `invite-code`, `invite-device`, `answer`, `devices` — права те же, что у телефона с той же ролью; вкладка «Управление узла» — список всех групп узла и удаление по паролю.

## Копии вагонов и второй исходный порт
Любой зашифрованный трафик между узлами уходит оригиналом и копией (`YANDI_WAGON_COPIES`, 2..3); получатель отбрасывает повтор окном повторов до расшифровки.
Копия может идти со второго исходного порта узла (порт даёт система), через промежуток `YANDI_COPY_SPACING_MS` (0..50, по умолчанию 3). Включается `YANDI_SECOND_PATH=1`.
По умолчанию выключено: NAT/файервол получателя пропускает только пакеты от адреса и порта, куда он сам слал, и копия с другого порта до него не дойдёт. Включение по умолчанию — после согласования путей (получатель пробивает порт B отправителя).
