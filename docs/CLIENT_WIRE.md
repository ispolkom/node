# Договорённость между приложением на телефоне и узлом (CLIENT_WIRE)

Реализовано в `src/mobile_api.rs`, проверяется `chaos/mobiletest.py` (22 проверки на настоящих узлах).

## Как телефон попадает на узел
1. Владелец включает вход для телефона: порт в `mobile_tls.json` (`{"port": 443}`) или `YANDI_MOBILE_TLS_PORT`, перезапуск узла.
2. В настройках узла карточка «Приложение на телефоне» → «Показать QR». В QR: `{host, port, pairing_code, tls_fingerprint, tls:true}`.
   Код — 6 цифр, один раз, живёт 5 минут; 5 неверных попыток сжигают его.
3. Приложение проверяет сертификат узла по отпечатку из QR (sha256 от DER), меняет код на токен (`POST /mobile/pair`). Узел хранит только хэш токена
   (`mobile_devices.json` в папке данных, права 0600). Устройств не больше 16.

Один и тот же порт и сертификат обслуживают: прокси для телефона (первый байт 0x05), этот API (запрос `/mobile/...`) и сайт-маскировку (остальное).

## Запросы (токен: `Authorization: Bearer ...`, для сокета можно `?token=`)
| Запрос | Ответ |

| `GET /mobile/contacts` | `{contacts:[{peer_id, display_name, online, is_manual}]}`; `peer_id` полный, если собеседник сейчас известен узлу, иначе короткий |
| `GET /mobile/chat/{peer}?limit=` | `{messages:[{id, from_peer_id, text, ts_ms}]}`; `peer` — полный или короткий |

| `GET /mobile/inbox` | сообщения от других людей новее подтверждённого этим устройством: `{id (=время, мс), from_peer_id, payload_b64, ts_ms}` |
| `POST /mobile/inbox/ack` `{ids}` | подтверждение (хранится на узле, переживает перезапуск) |
| `GET /mobile/proxy/info` | `{running, host, port, upstream}` |
| `GET /mobile/pubkey/{peer}` | `{x25519_pub}` для другого телефона владельца, у обычных собеседников 404 |

## Сокет (двоичные кадры)
- `0x01` ping ↔ `0x02` pong.
- Сигнал звонка: телефон → узел `0x31` `[0x31][32 кому][4 длина LE][байты]`, узел → телефон `0x13` `[0x13][32 от кого][8 время мс LE][4 длина LE][байты]`. Доставляется только если адресат на связи и нигде не хранится; если его нет на связи, отправитель получает `0x14` `[0x14][32 номер]`. До 32 КБ, адресат — только другое устройство владельца.
- Узел → телефон `0x10`: `[0x10][32 от кого][8 время мс LE][4 длина LE][текст]`.
- Телефон → узел `0x30`: `[0x30][32 кому][4 длина LE][текст]`.

## Шифрование
Телефон↔узел: TLS с проверкой отпечатка. Узел↔узел: обычное сквозное шифрование чата. Своего слоя «телефон → собеседник» пока нет: узел не выдаёт
ключей, приложение отправляет обычный текст внутри TLS. Это решение владельца на будущее (узел владельца — доверенный).

## Известные границы
- Контакт, которого узел сейчас не знает, виден с коротким идентификатором, писать ему через сокет нельзя (кадр требует 32 байта) — через `POST /mobile/chat/{короткий}` тоже, пока он не появился в сети.
- Группы — см. «Группы» ниже (узел готов, приложение — следующим шагом).
- Телефон за NAT до компьютера за NAT не достучится: нужен компьютер с доступным адресом (белый IP или проброшенный порт) или цепочка через ретранслятор.


## Два телефона через один компьютер
- Каждый спаренный телефон — собеседник для остальных телефонов владельца: 64-значный номер (`device_id`, из `/mobile/info`), имя с 📱 в списке контактов, «в сети» — пока открыт его сокет. Изменения «в сети» приходят кадром `0x12`: `[0x12][32 номер][1 байт: 1 в сети / 0 нет]`.
- Сообщение другому телефону: тот же кадр `0x30` (или `POST /mobile/chat/{номер}`). Узел кладёт байты в очередь получателя (`mobile_mail.json`, права 0600) и сразу пересылает кадром `0x10`, если получатель на связи. Очередь чистится подтверждением (`inbox/ack`), как и обычные входящие.
- Узел байты не читает и не разбирает: приложение берёт ключ собеседника из `/mobile/pubkey/{номер}` и шифрует (`E2ECrypto`, первый байт 0xE2) — компьютер видит только шифртекст.
- Номер входящего (`id`) — его время в миллисекундах (одинаково в `inbox` и в кадре `0x10`), поэтому приложение не показывает одно сообщение дважды.

## Выход телефона в интернет
- Телефон открывает TLS до компьютера и просит `CONNECT хост:порт HTTP/1.1` с `Proxy-Authorization: Bearer <токен устройства>` (Basic: пароль = токен). Ответ `200` — дальше байты как есть; `407` — нет или чужой токен; `403` — цель закрыта (этот компьютер, домашняя сеть); `502` — не соединилось; `503` — больше 256 одновременных.
- Узел соединяется правилами выхода (`exit_policy::connect_public_for`): если у владельца включены внешние прокси (настройки узла) — только через них, имя цели передаётся прокси как есть.
- Внешних прокси может быть несколько (`upstream_proxy.json`, страница настроек узла). За каждым устройством закрепляется один прокси (все его соединения выходят с одного адреса); новое устройство получает наименее загруженный прокси, на котором есть место (по умолчанию до 5 устройств, предел общий и на каждый прокси отдельно; мягкий лимит сажает лишнее устройство на самый свободный, строгий отказывает: `502`). Не отвечающий прокси исключается на 10 секунд, дальше вдвое дольше, до 5 минут; его устройства переезжают на живые, а соединение, на котором прокси подвёл, повторяется на другом (до трёх попыток). Отказ самой цели прокси не штрафует. Если мертвы все, пробуется тот, у кого пауза кончается раньше; прямого выхода в обход прокси нет. Закрепление забывается после 30 минут молчания устройства.
- В приложении: небольшой прокси на самом телефоне (`127.0.0.1:10808`, понимает HTTP CONNECT, обычный HTTP и SOCKS5) + системный режим VPN без маршрутов, который объявляет этот прокси системе (Android 10+). Приложения, не уважающие системный прокси, и UDP/QUIC этим путём не идут.


## Файлы между телефонами
- Отправитель шифрует каждый кусок (256 КБ) сам: AES-256-GCM, ключ на файл, случайное число 12 байт в начале куска, метка 16 байт в конце; в проверяемые данные входят номер передачи, номер куска и их число (`yandi-file:v1|<id>|<n>|<всего>`), поэтому узел не может переставить, подменить или обрезать куски незаметно.
- Ключ, настоящее имя, размер, число кусков, тип и sha256 открытого файла уходят получателю обычным зашифрованным сообщением (`\u0001yandi-file:` и JSON). Узлу достаются только безликая подпись, размер, число кусков, кто кому и когда.
- Узел хранит куски на диске (`mobile_files/<id>/`), пока получатель не заберёт файл: до 7 дней (недокачанное — сутки). Лимиты: файл до 1 ГБ, до 4096 кусков, всего 4 ГБ на узле, до 20 незавершённых передач на отправителя. Получатель после скачивания сверяет размер и sha256 и удаляет передачу с узла.

## Звонки и видеозвонки
- Звук и видео идут по WebRTC и шифруются между самими телефонами (DTLS-SRTP). Описания сеанса и кандидаты едут «живыми» сигналами (`0x31`/`0x13`), зашифрованными телефоном для телефона (`\u0001yandi-call:` и JSON: `invite`, `accept`, `reject`, `busy`, `hangup`, `offer`, `answer`, `ice`); сигнал старше 90 секунд игнорируется.
- Телефоны в разных сетях соединяются через сервер звонков (coturn на компьютере владельца). Настраивается один раз: `sudo bash scripts/setup-turn.sh <внешний адрес>` (порт 3478 TCP/UDP и релейные UDP 50000–50199, схема временных паролей «REST API»: имя — срок и метка, пароль — HMAC-SHA1 от имени с общим секретом, который лежит только в `/etc/turnserver.conf` и `turn.json` узла). Сервер видит только зашифрованные пакеты и кто с кем соединён.
- Доверие: узел владельца доверенный для сигналов (он знает открытый ключ получателя); подмена отпечатка DTLS узлом возможна, как и подмена любого сообщения, поэтому он должен быть вашим.

## Группы
Реализовано в `src/mobile_groups.rs`, проверяется `chaos/grouptest.py`. Сервер группы — узел владельца; содержимое шифруют телефоны, узел его не читает.

- **Создать и удалить** группу можно только на компьютере (страница узла, `/api/mobile/groups`): название, тема, тип, устройство-владелец группы (у него ключ), начальные участники.
- **Типы:** `closed` — участников добавляет только компьютер; `invite` — вступают по коду приглашения `XXXX-XXXX-XXXX` (выдают владелец группы, модераторы или компьютер; узел хранит только хэш, срок по умолчанию сутки, число использований 1–50); `open` — любой телефон этого узла видит группу (`/mobile/groups/open`) и вступает сам. «Для всех» нет.
- **Псевдонимы:** в группе участник — случайный псевдоним этой группы («Тихий Лис-42»). Номера устройств в данных групп нет: участник записан хэшем `sha256("yandi-group-member:" группа ":" номер устройства)`, у каждой группы свой. Имя, которое человек называет при вступлении, он пишет зашифрованной записью в журнал.
- **Ключ группы** создаёт телефон-владелец. Каждый участник публикует свой открытый ключ для группы (x25519, `member_pub`), владелец запечатывает ключ группы каждому и кладёт конверты на узел (`POST keys`), участник забирает свой (`GET keys`). Поколение ключа (`epoch`) растёт при смене; после выхода, изгнания или запрета участника узел ставит владельцу `rekey_needed`. Узел видит конверты как непрозрачные байты. Доверие то же, что и для ключей телефонов: подменить `member_pub` может только сам узел (см. аудит #11).
- **Журнал** — только дописывание: запись `{seq, ts, from (псевдоним), epoch, payload_b64}`, до 64 КБ шифртекста. Телефон забирает «всё после N» (`GET log?after=N`, до 500 записей / 4 МБ за раз). На диске журнал группы не больше 32 МБ: старое уходит, номера сохраняются (`first_seq` растёт).
- **Намёк** в сокете: `0x15` `[0x15][16 номер группы][1 что][8 seq LE]`, что: `1` новая или стёртая запись, `2` ключи, `3` состав/настройки/роли, `4` группа удалена. Содержимого в намёке нет, приходит только участникам.
- **Модерация** (владелец группы и модераторы с телефона, компьютер — всё): `mute`/`unmute`, `kick`, `ban`/`unban` (запрещённый не вернётся ни по коду, ни в открытую), `delete_entry` (байты записи стираются с диска, номер остаётся с `deleted:true`), `promote`/`demote` (только владелец группы). Модератор не трогает владельца и других модераторов. Всё пишется в журнал модерации (до 1000 записей, видят участники). Запрет ссылок/медиа — дело приложения.
- Устройство, которое узел забыл, выпадает из всех групп. Владелец группы выйти не может — сменить владельца можно на компьютере (`/owner`).

Устройство указывается началом номера из списка устройств.
