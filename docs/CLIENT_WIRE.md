# Договорённость между приложением на телефоне и узлом (CLIENT_WIRE)

Реализовано в `src/mobile_api.rs`, проверяется `chaos/mobiletest.py` (22 проверки на настоящих узлах).

## Как телефон попадает на узел
1. Владелец включает вход для телефона: порт в `mobile_tls.json` (`{"port": 443}`) или `YANDI_MOBILE_TLS_PORT`, перезапуск узла.
2. В настройках узла карточка «Приложение на телефоне» → «Показать QR». В QR: `{host, port, pairing_code, tls_fingerprint, tls:true}`.
   Код — 6 цифр, один раз, живёт 5 минут; 5 неверных попыток сжигают его.
3. Приложение проверяет сертификат узла по отпечатку из QR (sha256 от DER), меняет код на токен (`POST /mobile/pair`). Узел хранит только хэш токена
   (`mobile_devices.json` в папке данных, права 0600). Устройств не больше 16.

Один и тот же порт и сертификат обслуживают: прокси для телефона (первый байт 0x05), этот API (запрос `/mobile/...`) и сайт-маскировку (остальное).

## Запросы (токен: `Authorization: Bearer ...`, для сокета можно `?token=`)
| Запрос | Ответ |
|---|---|
| `POST /mobile/pair` `{pairing_code, device_name}` | `{token}` |
| `GET /mobile/info` | `{node_id (64 hex), name, version}` |
| `GET /mobile/contacts` | `{contacts:[{peer_id, display_name, online, is_manual}]}`; `peer_id` полный, если собеседник сейчас известен узлу, иначе короткий |
| `GET /mobile/chat/{peer}?limit=` | `{messages:[{id, from_peer_id, text, ts_ms}]}`; `peer` — полный или короткий |
| `POST /mobile/chat/{peer}` `{text}` | `{id, ts_ms}` |
| `GET /mobile/inbox` | сообщения от других людей новее подтверждённого этим устройством: `{id (=время, мс), from_peer_id, payload_b64, ts_ms}` |
| `POST /mobile/inbox/ack` `{ids}` | подтверждение (хранится на узле, переживает перезапуск) |
| `GET /mobile/proxy/info` | `{running, host, port, upstream}` |
| `GET /mobile/pubkey/{peer}` | `{x25519_pub, ed25519_pub, signature}` для телефона владельца или самого узла; у обычных собеседников 404 |
| `POST /mobile/pubkeys` `{ed25519_pub, x25519_pub, signature}` | телефон регистрирует подписанную связку ключей |
| `POST /mobile/files` `{to_peer_id, file_name, file_size, total_chunks}` | `{transfer_id, chunk_max}` — начать передачу другому своему устройству (см. «Файлы между телефонами») |

| `GET /mobile/files/{id}/status` | `{done, total_chunks, file_size, have:[...]}` — для докачки |
| `GET /mobile/files` | `{files:[{id, from_peer_id, file_name, file_size, total_chunks, created_ms}]}` — готовые файлы для этого устройства |
| `GET /mobile/files/{id}/chunk/{n}` | байты куска (получатель или отправитель, когда передача завершена) |
| `DELETE /mobile/files/{id}` | получатель после скачивания или отправитель при отмене |
| `GET /mobile/turn` | `{host, port, username, credential, ttl}` — временные данные сервера звонков, `404`, если он не настроен |
| `GET /mobile/ws` | сокет сообщений |

## Сокет (двоичные кадры)
- `0x01` ping ↔ `0x02` pong.
- Сигнал звонка: телефон → узел `0x31` `[0x31][32 кому][4 длина LE][байты]`, узел → телефон `0x13` `[0x13][32 от кого][8 время мс LE][4 длина LE][байты]`. Доставляется только если адресат на связи и нигде не хранится; если его нет на связи, отправитель получает `0x14` `[0x14][32 номер]`. До 32 КБ, адресат — только другое устройство владельца.
- Узел → телефон `0x10`: `[0x10][32 от кого][8 время мс LE][4 длина LE][текст]`.
- Телефон → узел `0x30`: `[0x30][32 кому][4 длина LE][текст]`.

## Шифрование
Телефон↔узел: TLS с проверкой отпечатка. Между спаренными телефонами и в чате с самим ПК — аутентифицированный E4 (описан ниже). Узел↔узел использует свой отдельный транспорт чата. Если проверенная связка получателя недоступна, Flutter не отправляет сообщение: plaintext fallback отсутствует.

## Известные границы
- Контакт, которого узел сейчас не знает, виден с коротким идентификатором, писать ему через сокет нельзя (кадр требует 32 байта) — через `POST /mobile/chat/{короткий}` тоже, пока он не появился в сети.
- Группы — см. «Группы» ниже (узел готов, приложение — следующим шагом).
- Телефон за NAT до компьютера за NAT не достучится: нужен компьютер с доступным адресом (белый IP или проброшенный порт) или цепочка через ретранслятор.


## Два телефона через один компьютер
- Каждый спаренный телефон — собеседник для остальных телефонов владельца: 64-значный номер (`device_id`, из `/mobile/info`), имя с 📱 в списке контактов, «в сети» — пока открыт его сокет. Изменения «в сети» приходят кадром `0x12`: `[0x12][32 номер][1 байт: 1 в сети / 0 нет]`.
- Сообщение другому телефону: тот же кадр `0x30` (или `POST /mobile/chat/{номер}`). Узел кладёт байты в очередь получателя (`mobile_mail.json`, права 0600) и сразу пересылает кадром `0x10`, если получатель на связи. Очередь чистится подтверждением (`inbox/ack`), как и обычные входящие.
- Между телефонами узел байты не расшифровывает: приложение берёт подписанную связку из `/mobile/pubkey/{номер}`, закрепляет Ed25519 и шифрует E4. В переписке с самим ПК узел — конечная точка и расшифровывает для своего UI.
- Номер входящего (`id`) — его время в миллисекундах (одинаково в `inbox` и в кадре `0x10`), поэтому приложение не показывает одно сообщение дважды.

## Выход телефона в интернет
- Телефон открывает TLS до компьютера и просит `CONNECT хост:порт HTTP/1.1` с `Proxy-Authorization: Bearer <токен устройства>` (Basic: пароль = токен). Ответ `200` — дальше байты как есть; `407` — нет или чужой токен; `403` — цель закрыта (этот компьютер, домашняя сеть); `502` — не соединилось; `503` — больше 256 одновременных.
- Узел соединяется правилами выхода (`exit_policy::connect_public_for`): если у владельца включены внешние прокси (настройки узла) — только через них, имя цели передаётся прокси как есть.
- Внешних прокси может быть несколько (`upstream_proxy.json`, страница настроек узла). За каждым устройством закрепляется один прокси (все его соединения выходят с одного адреса); новое устройство получает наименее загруженный прокси, на котором есть место (по умолчанию до 5 устройств, предел общий и на каждый прокси отдельно; мягкий лимит сажает лишнее устройство на самый свободный, строгий отказывает: `502`). Не отвечающий прокси исключается на 10 секунд, дальше вдвое дольше, до 5 минут; его устройства переезжают на живые, а соединение, на котором прокси подвёл, повторяется на другом (до трёх попыток). Отказ самой цели прокси не штрафует. Если мертвы все, пробуется тот, у кого пауза кончается раньше; прямого выхода в обход прокси нет. Закрепление забывается после 30 минут молчания устройства.
- В приложении: небольшой прокси на самом телефоне (`127.0.0.1:10808`, понимает HTTP CONNECT, обычный HTTP и SOCKS5) + системный режим VPN без маршрутов, который объявляет этот прокси системе (Android 10+). Приложения, не уважающие системный прокси, и UDP/QUIC этим путём не идут.


## Файлы между телефонами
- Отправитель шифрует каждый кусок (256 КБ) сам: AES-256-GCM, ключ на файл, случайное число 12 байт в начале куска, метка 16 байт в конце; в проверяемые данные входят номер передачи, номер куска и их число (`yandi-file:v1|<id>|<n>|<всего>`), поэтому узел не может переставить, подменить или обрезать куски незаметно.
- Ключ, настоящее имя, размер, число кусков, тип и sha256 открытого файла уходят получателю обычным зашифрованным сообщением (`\u0001yandi-file:` и JSON). Узлу достаются только безликая подпись, размер, число кусков, кто кому и когда.
- Узел хранит куски на диске (`mobile_files/<id>/`), пока получатель не заберёт файл: до 7 дней (недокачанное — сутки). Лимиты: файл до 1 ГБ, до 4096 кусков, всего 4 ГБ на узле, до 20 незавершённых передач на отправителя. Получатель после скачивания сверяет размер и sha256 и удаляет передачу с узла.

## Квитанции файлов компьютер ↔ телефон

- Телефон → компьютер: после проверки размера/sha256, сохранения файла и сообщения узел шлёт зашифрованный `\u0001yandi-rcpt:{"kind":"delivered","ids":["file_<tid>"]}`. При открытии истории на странице — `read` по тому же ID. При ошибке приёма успешная квитанция не отправляется.
- Компьютер → телефон: предложение `\u0001yandi-file:{...}` вложено в `\u0001yandi-msg:{"v":1,"cmid":"<полный msg_id hex>","text":"<предложение>"}` и затем шифруется E4. Приложение распаковывает конверт до разбора `FileOffer`, отправляет `delivered` при сохранении предложения и `read` при открытии чата. Эти квитанции относятся к сообщению с предложением; скачивание файла — отдельное действие.
- Файловый v1 и кадры WebSocket не менялись; полезная нагрузка сообщений обновлена до E4. Kotlin-сервис не расшифровывает payload и показывает общее уведомление; поля E4 обрабатывает только Dart.

## Аутентифицированный конверт E4 (ПК и телефоны)

Заголовок 134 байта: `[E4][kind:1][from:32][to:32][random_id:16][timestamp_ms:u64 BE][ephemeral_x25519:32][nonce:12]`. Kind 1 — почта/чат/квитанции/предложения файлов; 2 — живые сигналы. From/to — транспортные 32-байтовые ID, у телефона **device_id из /mobile/info**, не hex Ed25519.

После заголовка: AES-256-GCM ciphertext+tag16, затем Ed25519 signature64. AAD = `YANDI-E2E-E4\0` + весь заголовок. Ключ AES = HKDF-SHA256(shared X25519, salt=SHA256(AAD), info=`YANDI-E2E-E4-KEY`, len=32). Нулевой DH запрещён. Подпись над `YANDI-E2E-E4-SIGN\0` + заголовок + ciphertext/tag. Получатель сначала сверяет ожидаемые адреса и kind, свежесть и подпись по закреплённому Ed25519; после AEAD/UTF-8 атомарно сохраняет from+to+random_id в дисковый ledger, до передачи текста дальше.

Срок 30 суток от подписанного времени, допустимое опережение часов 5 минут. Истёкшие ID удаляются только когда соответствующие конверты уже недопустимы; свежие ID не вытесняются. Лимит 100000, повреждение/ошибка записи/переполнение — отказ, без сброса защиты. Ledger общий для сокета/inbox, сохраняется при reconnect/restart. Откат часов/данных ОС и удаление ledger владельцем/root не входят в гарантию. Возможен отказ доставки при аварии после записи replay, но до сохранения сообщения: нужна будущая общая транзакция с историей.

Связка проверяется Ed25519 и закрепляется TOFU в secure storage телефона. Изменение Ed — отказ и предупреждение; X25519 можно обновить под прежней подписью. Отпечатки SHA-256 Ed доступны в чате для независимого сравнения. Первое TOFU не доказывает личность против злонамеренного первого ретранслятора. ПК не принимает смену Ed по тому же bearer-token (409); смена identity требует нового сопряжения. Подтверждение регистрации выдаётся после успешной постоянной записи.

Обновление несовместимо с E2/E3: fallback запрещён. До выпуска обновить одновременно узел и все приложения. Старые E2/E3 сообщения в inbox новый клиент не подтверждает и не удаляет: требуется отдельное согласованное решение о переносе/повторной отправке. Готовые скачанные файлы/локальная история не меняются. Сетевой прогон и проверка на реальных устройствах обязательны до release.
- Стенд для Claude: `YANDI_TEST_FILE_RECEIPTS=1 python3 chaos/mobiletest.py` с установленным Python `cryptography`. Включает обе стороны, скачивание/расшифровку и запрет понижения `Read` обратно в `Delivered`.

## Звонки и видеозвонки
- Звук и видео идут по WebRTC и шифруются между самими телефонами (DTLS-SRTP). Описания сеанса и кандидаты едут «живыми» сигналами (`0x31`/`0x13`), зашифрованными телефоном для телефона (`\u0001yandi-call:` и JSON: `invite`, `accept`, `reject`, `busy`, `hangup`, `offer`, `answer`, `ice`); сигнал старше 90 секунд игнорируется.
- Телефоны в разных сетях соединяются через сервер звонков (coturn на компьютере владельца). Настраивается один раз: `sudo bash scripts/setup-turn.sh <внешний адрес>` (порт 3478 TCP/UDP и релейные UDP 50000–50199, схема временных паролей «REST API»: имя — срок и метка, пароль — HMAC-SHA1 от имени с общим секретом, который лежит только в `/etc/turnserver.conf` и `turn.json` узла). Сервер видит только зашифрованные пакеты и кто с кем соединён.
- Доверие: узел владельца доверенный для сигналов (он знает открытый ключ получателя); подмена отпечатка DTLS узлом возможна, как и подмена любого сообщения, поэтому он должен быть вашим.

## Группы
Реализовано в `src/mobile_groups.rs`, проверяется `chaos/grouptest.py`. Сервер группы — узел владельца; содержимое шифруют телефоны, узел его не читает.

- **Создать** группу может телефон (`POST /mobile/groups {name, topic, about?, kind: invite|open}`, до 10 групп на устройство): он становится владельцем, ключ группы и права раздаёт он. **Удалить** группу целиком можно только на странице «Группы» (`/groups`, вкладка «Управление узла»), с повторным вводом пароля узла (`POST /api/mobile/groups/{id}/delete {password}`, неверные попытки считаются как при входе); модерацией, участниками, приглашениями и владельцем с компьютера управлять нельзя — это права телефона-владельца и его модераторов. Запасной путь: страница узла создаёт группу (`closed` — только так) с обязательным телефоном-владельцем.
- **Типы** (их два): `invite` — «по приглашению»: вступают по коду `XXXX-XXXX-XXXX` (выдают владелец группы и модераторы; узел хранит только хэш, срок по умолчанию сутки, число использований 1–50) либо попросив приглашение; `open` — «открытая»: вступают сразу. Старый тип `closed` в данных читается как `invite`; при создании не принимается. «Для всех» (вне узла) нет.
- **Тематика и описание:** у новой группы тематика обязательна (короткая метка до 40 знаков, нужна для каталога и будущих фильтров), описание необязательно (до 300 знаков); пустые поля в карточке не показываются.
- **Псевдонимы:** в группе участник — случайный псевдоним этой группы («Тихий Лис-42»). Номера устройств в данных групп нет: участник записан хэшем `sha256("yandi-group-member:" группа ":" номер устройства)`, у каждой группы свой. Имя, которое человек называет при вступлении, он пишет зашифрованной записью в журнал.
- **Ключ группы** создаёт телефон-владелец. Каждый участник публикует свой открытый ключ для группы (x25519, `member_pub`), владелец запечатывает ключ группы каждому и кладёт конверты на узел (`POST keys`), участник забирает свой (`GET keys`). Поколение ключа (`epoch`) растёт при смене; после выхода, изгнания или запрета участника узел ставит владельцу `rekey_needed`. Узел видит конверты как непрозрачные байты. Доверие то же, что и для ключей телефонов: подменить `member_pub` может только сам узел (см. аудит #11).
- **Журнал** — только дописывание: запись `{seq, ts, from (псевдоним), epoch, payload_b64}`, до 64 КБ шифртекста. Телефон забирает «всё после N» (`GET log?after=N`, до 500 записей / 4 МБ за раз). На диске журнал группы не больше 32 МБ: старое уходит, номера сохраняются (`first_seq` растёт).
- **Намёк** в сокете: `0x15` `[0x15][16 номер группы][1 что][8 seq LE]`, что: `1` новая или стёртая запись, `2` ключи, `3` состав/настройки/роли, `4` группа удалена. Содержимого в намёке нет, приходит только участникам.
- **Роли и права:** *владелец* (один) — всё; *админ* — настройки группы, правила, роли «модератор/участник», действия модератора, не трогает владельца и других админов; *модератор* — `mute`/`unmute`, `kick`, `ban`/`unban` (запрещённый не вернётся ни по коду, ни в открытую), `delete_entry` (байты записи стираются, номер остаётся с `deleted:true`), приглашения, просьбы; трогает только рядовых; *участник* — читает и пишет. Роли назначаются действиями `make_admin` (только владелец), `promote` (→ модератор) и `demote` (→ участник) (владелец и админ). Правила группы принимаются клиентами от владельца и админов. Всё пишется в журнал модерации (до 1000 записей, видят участники). Запрет ссылок/медиа — дело приложения.
- Устройство, которое узел забыл, выпадает из всех групп. Владелец группы выйти не может — сменить владельца можно на компьютере (`/owner`).

| `POST /mobile/groups/{id}/owner` `{alias}` | **передача владения** (только владелец): прежний владелец становится админом, узел ставит `rekey_needed`, новый владелец создаёт новое поколение ключа; `409` — у участника нет ключа группы, `403` — не владелец. Перед этим приложение кладёт в ленту служебную запись `{op:"handover", to:псевдоним, pub:ключ нового владельца}`: по ней остальные клиенты перезакрепляют ключ владельца (принимается, только если новый владелец по списку узла называет именно этот ключ и запись написал другой руководитель — прежний владелец/админ, а не сам новый владелец). Владелец забирает недостающие старые поколения ключа по закреплённому ключу прежнего |

**Файлы групп** (`src/mobile_group_files.rs`): узел хранит только шифртекст кусков (ключ файла лежит внутри зашифрованной записи журнала, поэтому узел не знает ни имени, ни содержимого). До 200 МБ на файл, 2 ГБ на группу, 8 ГБ на все группы узла; готовый файл хранится 30 суток, недокачанный — сутки; не более 5 незавершённых заливок на участника. Скачать — любой участник (не выгнанный); залить — не заглушённый; стереть — залившего, модератор, владелец группы. Удалили группу — удалились и файлы. Кусок в AAD связан с номером файла, индексом и числом кусков (`FileCrypto`), запись журнала несёт `{f, n, z, c, k, h}` (номер на узле, имя, размер, число кусков, ключ, sha256).

| `PUT /mobile/groups/{id}/files/{fid}/chunk/{n}` (двоичное тело) | `200` |
| `POST /mobile/groups/{id}/files/{fid}/done` | `{ok}`; `409 {missing:[…]}` — не хватает кусков |
| `GET /mobile/groups/{id}/files/{fid}` | `{done, total_chunks, file_size, have:[…]}` |
| `GET /mobile/groups/{id}/files/{fid}/chunk/{n}` | двоичный кусок (файл готов) |
| `DELETE /mobile/groups/{id}/files/{fid}` | `200` |

Страница узла (вход по паролю, только этот компьютер): `GET/POST /api/mobile/groups` (список с участниками и `devices`; создать `{name, topic, kind, owner_device, members}`), `POST /api/mobile/groups/{id}/delete {password}` (удалить с журналом и файлами), `GET .../modlog` (только чтение). Приглашение контакту уходит обычным зашифрованным сообщением `\u0001yandi-gi:{"g":номер,"c":код,"n":название}`. Устройство указывается началом номера из списка устройств.

## Аватарки
Служебные E2E-конверты (внутри обычного зашифрованного сообщения E4, kind=1; узел видит только шифртекст):
- `\u0001yandi-avh:{"h":"<sha256 hex>"}` — «моя картинка сейчас такая»; пустой `h` — картинки нет/убрана;
- `\u0001yandi-avq:{"h":"<hex>"}` — «пришли картинку с этим хэшем»;
- `\u0001yandi-ava:{"h":"<hex>","png":"<base64>"}` — картинка.

Правила: PNG не больше 40 КБ (вместе с base64 и шифрованием это укладывается в предел одного сообщения узла, 64 КБ), собирается заново из пикселей (центральный квадрат ≤128×128), поэтому EXIF/GPS/время/модель телефона/XMP/эскизы не переносятся. Хэш — SHA-256 байт PNG: одинаковые картинки у разных людей хранятся одним файлом, а привязка «контакт → хэш» у каждого своя (контакты не путаются). Картинку принимает только сохранённый контакт, не заблокированный и не сам узел; принимается лишь запрошенная, с совпавшим хэшем и читаемая декодером; свою отдаёт только по запросу с её хэшем. Хэш объявляется контакту при его появлении в сети (раз за сеанс) и раз в 6 часов. Узел неизвестные служебные конверты (`\u0001yandi-…`), в том числе аватарки, молча отбрасывает (`Envelope::Ignored`), чтобы они не показывались на странице чата. Аватарки ПК (профиль страницы узла) в этом протоколе пока не участвуют.

## Группы на компьютере (узел как участник)
Реализовано в `src/group_client.rs`, проверяется `chaos/pcgroups.py` (телефон-эмулятор с настоящей криптографией) и контрольными векторами из приложения (`tests/data/group_vector.json`, сгенерированы `mobile/yandi_mobile/test/gen_group_vectors_test.dart`). Для групп компьютер — такое же устройство, как телефон: номер участника — хэш от номера узла и группы, свой ключ x25519 на каждую группу, вступает по приглашению или просьбе, создаёт группы и владеет ими. Содержимое расшифровывается только в группах, где узел состоит сам. Формат шифрования байт-в-байт как в приложении (`group_crypto.dart`). На диске (`groups_pc/`, права 0600/0700) всё закрыто AES-256-GCM-ключом из мастер-ключа узла: состояние (закрытые ключи участника, ключи групп, закреплённые ключи владельцев) и расшифрованная лента; без мастер-ключа каталог ничего не даёт. Страница — `/groups` (вкладка «Мои группы»), ручки `/api/groups...` (только вошедшему в админку); вкладка «Управление узла» — список всех групп узла, журнал, удаление по паролю и запасное создание (`/api/mobile/groups...`).
