# Усиление рукопожатия (этап 2б) — проект

Статус: **проект, код не менялся**; независимая проверка Sol — до реализации. Основание — находки P15-3…7 и P15-12 (`ANALYSIS15.md`). Этап 2а (удаление RESUME и секретов) от этого проекта не зависит и уже сделан; этап 2б нужен, чтобы «восстановление соединения новым рукопожатием» было действительно надёжным.

## 1. Что есть сейчас (по коду)
- `HelloPacket` (`src/netlayer/packet.rs`): тип `Request`/`Ack`, подпись Ed25519 над `challenge_data()` (метка `yandi-hello-v2`, тип, версия, `node_id`, `node_name`, ключ подписи, **эфемерный X25519**, cid, возможности, время, `nonce`, адреса, юрисдикция). Самосертифицируемая личность: `node_id` выводится из ключа подписи (`verify_peer_handshake_static`), окно времени ±5 минут, защита от повторов `seen_hello_nonces` (в памяти).
- Ответчик, получив `Request`, **сразу** выводит ключ (`complete_hello_responder`) и сохраняет сеанс (`send_hello_ack`, `transport.rs` ~4481) — до того, как инициатор что-либо доказал. `Ack` подписан, но его собственные данные не содержат ни хэша запроса, ни ожидаемой личности инициатора; соответствие определяется по `request_nonce` (UDP) или не проверяется вовсе (WS-клиент проверяет только подпись `Ack`).
- Инициатор, получив `Ack`, выводит ключ и публикует маршрут (`ws_outgoing`) сразу; подтверждения ключа нет.
- Учёт нагрузки: `admit_peer` ограничивает число **принятых** Hello, но проверка подписи происходит до него; на WS replay-кэш вставляется до допуска.
- Что именно защищает от подмены: подписанный эфемерный ключ делает участника аутентифицированным; но ответ не связан с запросом и сеанс ответчика становится активным без доказательства со стороны инициатора.

## 2. Угрозы (из проверки Sol, подтверждённые чтением кода)
1. **Запись Hello (и после перезапуска узла кэш повторов пуст) может заново создать у ответчика сеанс с эфемерным ключом из записи** — атакующий ключ не вычислит, но состояние ответчика для этого пира подменяется (разрыв действующего сеанса, замусоривание таблиц, публикация адреса/маршрута).
2. `Ack` не привязан к запросу и ожидаемому участнику: чужой/старый корректно подписанный `Ack` может быть принят вместо нужного (WS: проверяется только подпись).
3. Нет **подтверждения ключа**: ни одна сторона не знает, что другая вывела тот же ключ, прежде чем начнёт использовать его и публиковать маршрут; старое соединение может продолжать использовать прежний ключ, пока новый маршрут уже виден.
4. Нет **живости** инициатора: подписанного свежего вызова ответчика нет.
5. Подпись проверяется до дешёвых бюджетов: атакующий с малой стоимостью заставляет узел тратить Ed25519/X25519.
6. Политика «только сопряжённые» не определена (запись права `paired_clients` нигде не проверяется при входе).
7. Стирание ключей: не доказано, что расписание ключей AES и промежуточные значения затираются.

## 3. Предлагаемая конструкция (версия рукопожатия 3, без отката)
Основа остаётся прежней (подписанный Hello с эфемерным X25519); меняется связывание и подтверждение. Стандартный образец — аутентифицированный обмен ключами «sigma-подобного» вида (подпись над транскриптом) с подтверждением ключа; примитивы те же: Ed25519, X25519, HKDF-SHA256, AES-256-GCM, MAC на HMAC-SHA256.

1. **Request** (инициатор → ответчик): прежний `Hello` с версией 3, эфемерный `Ea`, время, `nonce`. Подписан личностью инициатора (как сейчас).
2. **Ack** (ответчик → инициатор): содержит эфемерный `Eb`, случайный **вызов** `Cb` (16 байт), `request_hash = SHA-256(Request || подпись Request)`, `expected_initiator = node_id` из Request, и подпись личностью ответчика над всем этим плюс собственные поля Hello. Ответчик **не создаёт активный сеанс**: в таблице «ожидающих» остаётся запись (ключ — `request_hash`) с TTL ≤ 10 секунд и общим пределом числа.
3. **Транскрипт** `T = SHA-256("yandi-hs-v3" || Request || Ack)`. Ключи: `PRK = HKDF-Extract(salt = T, ikm = DH(Ea, Eb))`; ключи трафика по направлениям, ключи подтверждения `Kc_i`, `Kc_r` — отдельные метки HKDF.
4. **Finished** (инициатор → ответчик): `MAC(Kc_i, T || Cb)`. Инициатор перед этим проверил: подпись `Ack`, `request_hash` своего запроса, `expected_initiator` = он сам, тип/версию, ожидаемую личность ответчика (если известна), отсутствие слабых точек X25519; только после этого выводит ключи.
5. **Finished от ответчика** (после проверки `Finished_i`): `MAC(Kc_r, T)` — инициатор повышает соединение до активного только когда получил его. Ответчик повышает «ожидающее» до активного **только** после верного `Finished_i`; до этого ничего не публикуется (ни `ws_outgoing`, ни `PeerInfo`, ни DHT, ни «онлайн»).
6. **Замена активного сеанса**: новый сеанс с тем же пиром ставится атомарно под замком этого пира и только после подтверждения; закрытие старого соединения не удаляет маршрут нового (уже есть `remove_route_if_same`); сообщения, ждавшие подтверждения, повторяются приложением (подтверждение доставки — уровень выше).
7. **Повторы**: запись Request, воспроизведённая позже или после перезапуска, приводит лишь к ожидающей записи с TTL и не может дать `Finished_i` (нужен закрытый `Ea`); кэш `seen_hello_nonces` остаётся дополнительным ограничением, а не доказательством. Для UDP: повторная отправка того же `Ack` по тому же `request_hash` идемпотентна.
8. **Бюджеты до подписи**: дешёвые проверки (размер, версия, структура, окно времени) → ограничитель на адрес и общий → ограниченный пул работы для Ed25519/X25519 → допуск. Журналы отказов ограничены по частоте. Известные законные пиры получают отдельный бюджет переподключения, чтобы чужие повторы не расходовали их квоту.
9. **Политика допуска**: сначала фиксируем роли — «узел сети (mesh)», «сопряжённый клиент якоря» — и действия, доступные каждой; запись права проверяется общим авторизатором **после** проверки подписи и **до** вставки в кэш повторов, публикации адреса и создания сеанса (для WS-ветки и UDP-ветки одинаково); для исходящего WS клиент проверяет ожидаемого якоря по сохранённой записи до установки ключа; задаются нормализация ключа, конечный срок, область действия, отзыв с закрытием живых каналов, повторная проверка перед фиксацией после `await`. Mesh-допуск остаётся открытым, как сейчас.
10. **Стирание**: `Zeroizing` для всех промежуточных значений (DH, PRK, ключи), проверка включённых возможностей `zeroize` у `aes`/`aes-gcm`/`x25519-dalek`/`ed25519-dalek`; таймаут и отмена «ожидающих»; core dump, swap и гибернация — эксплуатационные копии секретов, протокол их не очищает (записывается в документе).

## 4. Совместимость и миграция
- Версия Hello 3; узлы версии 2 не принимаются как равные (на ранней стадии проекта допустимо), автоматического отката на версию 2 нет. Диагностика без секретов: «пир использует несовместимую версию рукопожатия».
- UDP и WS используют один и тот же код проверки и разные транспорты; изменение не затрагивает формат пользовательских сообщений (E4) и транспортные пакеты после установления сеанса.

## 5. Тесты (автоматические, с честными оракулами)
1. Обычное рукопожатие по UDP и по WS даёт активные сеансы на обеих сторонах; ключи трафика — независимые от прежнего сеанса.
2. Воспроизведённый Request (в процессе и после перезапуска ответчика): активного сеанса нет, действующий сеанс не затронут, маршрут не опубликован.
3. `Ack` для другого запроса / от другой личности / с другим `expected_initiator` отвергается без потребления ожидающей записи.
4. Подмена любого поля Request/Ack (без переподписи) — отказ; новый валидный запрос законного участника — допустимое новое рукопожатие.
5. Нет `Finished_i` в срок — ожидающая запись исчезает, сеанс не создан; неверный MAC не меняет состояние.
6. Два одновременных рукопожатия с одним пиром (в том числе встречные): остаётся ровно один согласованный активный сеанс; старое соединение не стирает новое.
7. Лимиты: поток Hello с малой стоимостью для атакующего не вызывает больше N проверок подписи в секунду; законный пир не лишается квоты чужими повторами; границы 20/21 с контролируемыми часами.
8. Политика допуска: клиент без записи права не получает привилегированных действий; отозванное право закрывает живой канал.
9. Стирание: после закрытия сеанса ключевые структуры обнулены (где проверяемо); нет утечки ключей в журналы.
10. Регрессия: существующие `hello_*`-тесты, `testnet_*` (сообщения, файлы, rekey) проходят.

## 6. Что проект НЕ обещает
Прямая секретность относится к сеансам транспорта между соседями; пользовательский E2E-слой (`docs/E2E_ARCHITECTURE.md`) — отдельно. Анонимность и скрытие метаданных не обеспечиваются. Компрометация работающей машины раскрывает её текущие сеансы.

## 7. Порядок
1) проверка проекта Sol; 2) реализация отдельными коммитами (формат Hello v3 → ожидающие записи и Finished → публикация маршрута после подтверждения → бюджеты → политика допуска → стирание); 3) автотесты; 4) тесты на настоящих процессах и устройствах; 5) повторная проверка Sol; 6) статус в `docs/SECURITY_STATUS.md` меняется только после этого.
