# Подписанные выпуски ноды (Linux)

Цель: чтобы установленную или скачанную ноду нельзя было незаметно подменить. Принцип тот же, что у приложения: ключ подписи выводится из
фразы разработчика и нигде не хранится; открытый ключ публичен и закреплён у проверяющего.

## Что есть
- `src/release.rs` — манифест выпуска (версия, номер выпуска против отката, SHA-256 и размеры файлов) и подпись Ed25519 над точными
  байтами манифеста с доменным префиксом.
- `yandi-release` — инструмент: `pubkey`, `manifest`, `sign`, `verify`, `update`, `rollback`, `status`.
- `tools/node_release.sh` — сборка, детерминированный `tar.gz`, манифест, подпись, самопроверка.
- `release/yandi-release-pubkey.hex` — открытый ключ (создаётся при первой подписи, коммитится).
- `release/SEQ` — последний номер выпуска (коммитится, растёт на 1).

## Как выпускать
```
bash tools/node_release.sh          # спросит фразу (скрыто, дважды), создаст dist/yandi-node-<версия>-linux-<arch>/
bash tools/node_release.sh --check  # только проверить фразу по закреплённому ключу
```

## Как проверять скачанный выпуск
```
yandi-release verify <каталог выпуска> --pubkey <64 hex из release/yandi-release-pubkey.hex> --min-seq <номер установленного>
```
Выход `ВЫПУСК ВЕРЕН` означает: подпись манифеста верна ключом, подтверждённым у вас, seq не ниже указанного минимума (для проверки уже установленного архива равенство допустимо), каждый файл совпадает
по размеру и SHA-256. Любое иное — не устанавливать.

## Что это защищает и что нет
- Защищает цепочку поставки: подмену архива на сервере или по дороге, подмену отдельных файлов, откат на старый выпуск.
- НЕ защищает от запуска чужой модифицированной ноды на чужом компьютере: без аппаратной аттестации другой узел этого проверить не может.
- Проверять должен установщик/обновлятор или человек командой `verify`; запущенная нода сама себя проверить не может.
- Сам `yandi-release` нужно брать из доверенного источника (прошлый проверенный выпуск или сборка из исходников), иначе подменят проверяющего.

## Ключи
Один ключ подписи, без иерархии. Если фраза утекла или потеряна: выпускается новый ключ, его открытую часть нужно заново закрепить у
проверяющих вручную. Корневой ключ с ротацией и отзывом — следующий этап. Windows (.exe) и .deb с подписанным индексом — следующие этапы.

## Обновлятор Linux

Из доверенного экземпляра `yandi-release`:
```sh
yandi-release update --from /path/to/release --min-seq 0 --pubkey <64 hex> --install-dir "$HOME/.local/share/yandi-node"
yandi-release update --from https://server/releases/version --pubkey <64 hex> --install-dir "$HOME/.local/share/yandi-node" --min-seq N
yandi-release status --install-dir "$HOME/.local/share/yandi-node"
yandi-release rollback --install-dir "$HOME/.local/share/yandi-node"
```
Без `--install-dir` используется каталог `yandi-node` в пользовательском data-каталоге
(`XDG_DATA_HOME`, иначе `~/.local/share`). Root не нужен. Настройку `ExecStart` в systemd
на `<install>/yandi` делает владелец; обновлятор службу не меняет и не перезапускает.
После установки он печатает `sudo systemctl restart yandi-node`.

Перед записью в установочный каталог создаётся отдельный снимок выпуска, проверяются
подпись точных байтов манифеста, размеры и SHA-256 **всех** перечисленных файлов.
В манифесте нужен ровно один `.tar.gz`. HTTPS: системные доверенные CA, без proxy из
окружения, без любых перенаправлений; connect timeout 10 с, запрос 120 с, загрузка
выпуска ограничена 300 с (синхронная локальная распаковка этим таймером не прерывается).
Манифест ≤1 MiB, подпись ≤256 байт, файл ≤256 MiB, выпуск ≤512 MiB.
Архив: только ustar/простые GNU заголовки, ≤1 GiB содержимого и ≤4096 записей;
PAX/GNU long-name расширения, ссылки, устройства, повторные пути, абсолютные пути,
`..` и скрытые имена верхнего уровня запрещены. В корне должен быть обычный `yandi`.
Скрипты не запускаются. Права каталогов/исполняемых файлов 0755, остальных файлов 0644;
`yandi` всегда 0755; setuid/setgid не сохраняются.

Распаковка выполняется во временный каталог рядом с установочным. Каталоги версий
лежат в `<install>/.versions/`, `current` переключается одним `rename`.
Локальная запись `.release.json` находится внутри версии, поэтому видимые version/seq
и бинарник меняются вместе. `<install>/previous/` следует к прошлой версии через
`current/.previous`; `yandi` и `yandi-release` в корне — ссылки на `current`.
Операции установки/отката сериализованы `flock`, до переключения выполняется `fsync`.
Обрыв до переключения оставляет активную версию прежней; после переключения активна
полностью подготовленная новая версия. После SIGKILL могут оставаться временные и
неактивные каталоги: автоматической очистки истории нет.

`--min-seq` обязателен; 0 предназначен для первой установки. При миграции unmanaged
установки укажите её последний seq. `--current-seq` сохранён как совместимый alias.
Обновлятор требует seq строго больше max(указанный минимум, сохранённый max_seq). `rollback` — явный
локальный откат владельцем к previous; наибольший принятый seq сохраняется в новой
записи и продолжает запрещать сетевой/каталожный downgrade через `update`.
Повторная установка того же seq запрещена, включая seq уже принятого выпуска после rollback. Откат тоже переключает `current` атомарно,
сохраняя заменяемую версию как previous.

Имена `yandi`, `yandi-release`, `previous` в корне должны быть свободны либо уже
являться ссылками этой установки; обычные файлы с такими именами вызывают отказ.

Установочный каталог и его родитель должны принадлежать владельцу и быть защищены
от записи посторонними. Защита не распространяется на локального атакующего,
способного менять установщик, ключ, каталог версий или локальную запись seq.
Гарантии rename/fsync рассчитаны на обычную локальную Linux-ФС; потеря питания и
сетевые ФС требуют отдельной проверки. Уже работающий процесс продолжает исполнять
старую версию до перезапуска владельцем.

## Воспроизводимость

`tools/node_release.sh` использует общую рецептуру `tools/release_build_env.sh`:
`nice -n 15`, `CARGO_BUILD_JOBS=2`, `cargo build --release --locked --offline`, без
proxy-переменных. `CARGO_TARGET_DIR` по умолчанию
`/mnt/ssd480/wt/codex/target-updater`; `XDG_DATA_HOME=/tmp/codex_rf_xdg`.
`CARGO_ENCODED_RUSTFLAGS` устанавливается рецептурой (унаследованные flags заменяются):
исходники, target и Cargo home отображаются через `--remap-path-prefix` на стабильные
`/usr/src/yandi`, `/usr/src/yandi-target`, `/usr/src/cargo`.
`SOURCE_DATE_EPOCH` по умолчанию `1577836800`, допускается явное фиксированное значение.
Время манифеста также берётся из этой переменной. Архив ustar: сортировка имён,
uid/gid=0, фиксированное время и режимы файлов, gzip `-n -9`, `TZ=UTC`, `LC_ALL=C`.
В бинарники не добавляется собственное время сборки или путь сборочного каталога.

```sh
bash tools/node_release.sh --unsigned  # только сборка и архив, без фразы/подписи/SEQ
bash tools/repro_check.sh              # две независимые полные release-сборки
```
`repro_check.sh` копирует отслеживаемые **рабочие** файлы в два разных каталога
(новые файлы сначала нужно добавить в индекс), использует два независимых release-cache,
сохраняя заданный абсолютный `CARGO_TARGET_DIR`. Существующий release-cache временно
сохраняется и восстанавливается; параллельно запускать сборку в том же target нельзя.
Сравниваются SHA-256 архива, `yandi` и `yandi-release`; при различии сохраняются
`cmp`, `readelf` и `strings`-диагностики. Скрипт не подписывает и не изменяет ключ/SEQ.
Материалы двух сборок остаются в `.repro-check.*`; они содержат исходники и build-cache.

Условия сравнения: одинаковые исходники, Cargo.lock, SOURCE_DATE_EPOCH, открытый ключ
(если включён в архив), архитектура, rustc/Cargo, системные библиотеки/линкер,
GNU tar/gzip и локальный Cargo cache. `--offline` не заменяет заранее наполненный cache.
Это проверка сборки в разных путях на одном хосте, не обещание одинаковых байтов на
разных дистрибутивах или версиях toolchain. Номер seq выбирает владелец отдельно;
сравнение подписанного выпуска требует одинаковых seq и ключа, подпись в проверке
воспроизводимости не выполняется.

## Нормализация фразы v1

`derive_signing_key` сам применяет NFC (зафиксирован ICU4X 2.2.0), затем схлопывает
Unicode whitespace в одиночные пробелы. Соль `YANDI-NODE-RELEASE-KEY-V1` и параметры
Argon2id не изменены. Прежний `node_release.sh` уже применял NFC через Python:
ключ ранее закреплённых выпусков, созданных этим скриптом, сохранён. Для прямого
старого API/CLI-вызова с decomposed Unicode ключ изменится: это устранение прежнего
расхождения API и скрипта. Такой нестандартный закреплённый ключ нельзя незаметно
перепривязать; потребуется явная миграция владельцем. Боевой ключ/фраза в этой работе
не использовались. ASCII и уже NFC-фразы сохраняют прежний результат KDF.

Подписывающий скрипт держит `release/.lock` от начала сборки до конца проверки.
`release/SEQ` — канонический десятичный u64; номер резервируется атомарным rename
с fsync файла и каталога **до подписи**. Сбой может оставить пропуск, повтор номера
не допускается. Удалять/откатывать SEQ вручную нельзя. После первой публикации
сохраните SEQ вместе с закреплённым публичным ключом.
`--check` использует готовый доверенный `$CARGO_TARGET_DIR/release/yandi-release`,
требует существующий закреплённый ключ и ничего не собирает/записывает.
