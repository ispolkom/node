Статус: **проект до реализации**, пересмотрен после независимой проверки Codex (`ANALYSIS15`, 12 находок P15-1…12). Ничего ниже не объявляется исправленным.

> **Состояние (обновлено после круга 36):** этап 2а реализован частично и независимой проверкой не принят — см. `ANALYSIS16`/`docs/SECURITY_STATUS.md` (P16-1…10). Разделы 1–2 ниже описывают состояние **до** этапа 2а (исторически); текущая модель — `src/netlayer/pairing.rs` формата v2.

## 0. Что изменила проверка (итог)
Вариант A (убрать возобновление по сохранённым секретам) принят **как первый этап**, но проверка показала, что «просто положиться на существующий Hello» нельзя: у самого рукопожатия есть пробелы, не связанные с RESUME. Поэтому работа делится:

- **Этап 2а — убрать секреты и RESUME (делается сейчас).** Полностью удалить `0xC0/0xC1/0xC2` из ВСЕХ диспетчеров (WS и UDP), убрать `resume_secret_hex` и `session_key_hex` из токена, формат хранилищ v2 со строгим читателем и миграцией, санитизация копий и восстановления, тесты с исправленными оракулами. Это закрывает хранение рабочего ключа и секрета возобновления (R-1). Контроль доступа при этом не слабеет: `paired_clients` не использовался нигде, кроме RESUME, то есть «только сопряжённые» никогда не проверялось (P15-5).
- **Этап 2б — усиление рукопожатия (отдельный проект и отдельная проверка).** Ответ `HelloAck` привязать к полному запросу и ожидаемому участнику (P15-3), подтверждение ключа обеими сторонами и публикация маршрута только после него (P15-4, P15-6), бюджет проверки до подписи (P15-7), политика «только сопряжённые» с рабочим путём передачи ключа клиента (P15-5), полное уничтожение ключей (P15-12). Затрагивает всю сеть, поэтому — после утверждения проекта, а не вместе с 2а.
- Находки P15-1, P15-2, P15-10, P15-11 — исправления самого проекта (ниже учтены).

### Поправки к разделам 1–7 по итогам проверки
- **P15-1.** `set_session` вызывается боевым обработчиком `SESSION_ISSUE` (`transport.rs:5738`, `5797`), а не только тестами; генератор `encode_session_issue` вызывается лишь тестом, штатная выдача `/pair/issue` отдаёт JSON, `--import-pairing` не импортирует токен. То есть механизм приёма и fast path реализованы, но сквозного рабочего процесса выдачи → клиент → возобновление в продукте нет. Привязка к identity есть только в WS-пути (`resume_node_matches`, `node_id_hex`); в UDP-обработчике её нет (это подтверждение п. 1 исходного аудита). ACK — keyed BLAKE3 MAC, а не подпись личности. Удалять `0xC0/C1/C2` из всех диспетчеров.
- **P15-2.** Утверждение «повторы закрыты свежими значениями» неверно: запись RESUME можно предъявить заново и продлить срок токена. После 2а обработчиков нет вовсе; тест — что старый пакет не меняет права, ключи и маршруты.
- **P15-11.** «+1 RTT» — необоснованное обещание; цена измеряется отдельно (криптография, байты, квоты, общая задержка TCP/TLS/WS). Реальный предел частого переподключения — 20 Hello/мин на известный id. Выбор между A и B по RTT не делается.
- **P15-8 (миграция).** Отдельный читатель с результатами: нет файла / валидный v1 / строгий v2 / будущая версия / повреждён / ошибка прав или ввода-вывода. Мигрирует только валидный v1; любая другая ошибка не заменяется пустым состоянием. В v2 старые секретные поля **отвергаются**, а не молча игнорируются; обязательные поля без «небезопасных значений по умолчанию». Сохраняются `PairingPayload`, TLS-закрепление, URL и предпочтения клиента; обнуляется только право/сеанс. Блокировка на весь цикл чтение–преобразование–запись, запись в приватный каталог (`create_new`, 0600, `fsync` файла, атомарное переименование, `fsync` каталога); при сбое новое состояние не публикуется.
- **P15-9 (копии).** Санитизация на границах сбора и восстановления копии (`node_backup.rs`) до staging, независимо от запуска транспорта; учёт реального `--anchor-store`; инвентарь `before-restore`/`restore`/tmp. Предел гарантии: удаление и переименование не стирают старые блоки SSD/COW/снимков и внешние копии; ретроспективной прямой секретности для уже утёкших записей нет — можно лишь прекратить будущий RESUME и отозвать живые старые сеансы.
- **P15-10 (тесты).** Оракулы переписаны (раздел 7): изменение nonce БЕЗ переподписи — тест целостности; новый nonce с валидной подписью законного клиента — допустимое новое рукопожатие, а не повод для общего «отказа»; проверка файлов — по строгой схеме, декодированием штатным ключом теста и фикстурами известных секретов, а не по маске 64-hex; проверяется конечный результат (права, ключи, маршруты неизменны), не только `Result` одной функции.
- **P15-12.** Критерий приёмки 2б: проверка реально включённых `zeroize`-возможностей криптобэкендов (расписание ключей AES), `Zeroizing` для промежуточных значений, таймаут `pending`. Дампы памяти, подкачка, гибернация — эксплуатационные копии секретов, которые протокол не очищает.

## 2. Угрозы и слабости (что подтверждено чтением кода)
1. **Рабочий материал на диске.** Кто прочитал `paired_clients.json`/`paired_anchors.json` (кража файла, резервная копия, чтение процессом), получает `session_key` и `resume_secret`: может возобновить сеанс от имени клиента (или якоря) и **расшифровать любые записанные ранее возобновлённые сеансы** — клиентские и серверные числа идут по сети открыто, а ключ вычисляется из сохранённого `session_key`.
2. **Нет прямой секретности** возобновлённых сеансов: рабочий ключ не содержит ничего эфемерного.
3. **Секрет возобновления — симметричный MAC-ключ**, общий у обеих сторон: компрометация любой стороны позволяет подделать и клиента, и ответ узла.
4. Привязка к identity уже частично есть (`resume_node_matches`, `node_id_hex`, подпись ответа `compute_resume_ack_mac`), но она держится на секрете из п. 1; повторы закрыты свежими значениями обеих сторон.
5. **Выгода механизма невелика:** он экономит один обмен рукопожатием. Для этого он хранит долговременный секрет, который нужно защищать, и ломает прямую секретность.

## 3. Рассмотренные варианты
- **A. Убрать возобновление по сохранённым секретам; восстанавливать соединение обычным подписанным Hello+ECDH.** Рабочие ключи каждый раз новые (эфемерный X25519 с подписью Ed25519 личности обеих сторон), прямая секретность, на диске нет ни рабочего ключа, ни симметричного секрета. Цена — одно лишнее рукопожатие при каждом переподключении (WS: порядка одного RTT).
- **B. Новое возобновление: PSK + эфемерный X25519 + HKDF с привязкой ко всему транскрипту (как `psk_dhe_ke` в TLS 1.3).** Сохраняет скорость, даёт прямую секретность, но оставляет на диске предварительно разделённый секрет (его кража = подделка клиента), добавляет новый протокол, который надо проверять заново.
- **C. Только заменить `session_key_hex` на вывод через HKDF от другого секрета.** Отвергнуто (как и требует план): секрет рядом с токеном, прямой секретности нет.

**Рекомендация: вариант A.** Он удаляет класс уязвимостей, а не прячет его, и использует рукопожатие, которое уже работает и уже защищено подписью, свежестью и защитой от повторов. Вариант B возвращаем, только если измерения покажут, что лишнее рукопожатие вредит (мобильные сети, большое число переподключений); тогда он проектируется как отдельный протокол с независимой проверкой.

## 4. Что становится с токеном сопряжения
- *(Проектная формулировка; реализовано иначе, см. ниже.)* `SessionToken` теряет `resume_secret_hex` и `session_key_hex`. Остаётся **запись о праве**: `version`, `session_id`, `client_pubkey` (ключ подписи клиента), `node_id`, срок. **В действующем коде** `ClientGrant` хранит только `session_id_hex` и `expires_at`; ключ клиента записан отдельно как ключ записи в хранилище, а `node_id` в праве нет. Это не секрет: по ней нельзя ни расшифровать трафик, ни войти без закрытого ключа клиента.
- Вход клиента — подписанный Hello (самосертифицируемая личность). Политика «подключаются только сопряжённые клиенты» **в действующем коде не проверяется** — это задача этапа 2б (P15-5); ниже описан замысел: сверка `client_pubkey` из Hello с записями права в обработчике Hello, а не в отдельном протоколе возобновления.
- `POST /pair/issue` перестаёт возвращать и хранить секреты: принимает `client_pubkey_hex`, возвращает `session_id` и срок.
- Сообщения `0xC0` (RESUME), `0xC1` (ACK), `0xC2` (SESSION_ISSUE) и их разбор удаляются из WS- и UDP-путей. Никаких скрытых запасных веток к старой схеме.

## 5. Миграция
- Явная версия формата хранилищ (`"version": 2`). Читатель: запись без `version` или со старым форматом **не принимается как токен**; при загрузке файл переписывается без секретных полей (затирание: запись нового файла, `fsync`, переименование), в журнал — понятное сообщение без значений.
- Старые токены недействительны; клиент выполняет сопряжение заново (QR/`--import-pairing`). Проект на ранней стадии, обратная совместимость с внешними версиями не требуется.
- `node_backup.rs`: копии `paired_*.json` уже не содержат секретов; уже сделанные резервные копии со старыми секретами остаются у владельца — в документе по копиям это указано, рекомендация удалить старые копии.
- Перед удалением кода составлен перечень всех точек использования (раздел 1); после правки `grep` по `resume_secret|session_key_hex|new_with_session_key|encode_resume|decode_resume|0xC0 RESUME` обязан вернуть только тест миграции.

## 6. Остаточные риски (честно)
- Узел, работающий без владельца, держит в памяти действующие рабочие ключи текущих сеансов и свой долговременный ключ личности (`~/.yandi_keys`, запечатан ключом устройства). Компрометация **работающей** машины открывает текущие сеансы — это не лечится на уровне протокола.
- Запись права (`client_pubkey`) раскрывает, какие ключи сопряжены с узлом (метаданные); хранится рядом с остальными данными узла, права 0600.
- Лишнее рукопожатие при каждом переподключении увеличивает задержку и число подписей; измеряется на реальных устройствах (раздел 8).

## 7. Тесты (автоматические)
1. Клиент A сопрягается, теряет соединение и поднимает новое: рабочий ключ новый, обмен идёт.
2. Клиент B с токеном/идентификатором A не принят: личность в Hello не совпадает с записью права.
3. Записанное приветствие (Hello) проигрывается повторно — отказ (`seen_hello_nonces`).
4. Изменены identity, `session_id` или nonce — отказ; состояние действующих ключей не изменилось.
5. Два соединения подряд дают независимые ключи (сравнение ключей двух сеансов).
6. Повреждённый/подделанный пакет не меняет действующие ключи.
7. Файл старого формата (с `resume_secret_hex`/`session_key_hex`) не принимается и **переписывается без секретов**; старое поле нельзя прочитать как новое.
8. Содержимое `paired_clients.json`, `paired_anchors.json` и их копий не содержит ни 64-hex рабочего ключа, ни секрета возобновления (проверка по маске и по известным значениям).
9. Нет в коде обработчиков `0xC0/0xC1/0xC2` (тест-страж по исходникам).
10. Сценарий кражи файлов состояния: имея только файлы, нельзя ни расшифровать записанный трафик, ни подключиться (нужен закрытый ключ клиента).

## 8. Испытания на реальных процессах и устройствах (планируются, пока **не проведены**)
