# RESUME и хранение ключей сеанса — проект исправления (этап 2 плана безопасности)

Статус: **проект до реализации**; независимая проверка Codex — до начала правок. Ничего ниже не объявляется исправленным.

## 1. Что есть сейчас (по коду)
| Элемент | Где | Что хранится / делается |
|---|---|---|
| `SessionToken` | `src/netlayer/pairing.rs` | `session_id`, `resume_secret_hex` (32 Б, ключ MAC), `session_key_hex` (32 Б AES-ключ **открытым hex**), `node_id_hex`, срок |
| Хранилища | `paired_clients.json` (якорь), `paired_anchors.json` (клиент), копии в `node_backup.rs` | токены целиком, права 0600 |
| Выдача | `POST /pair/issue` (`web/server.rs`) | генерирует `session_key`, кладёт в хранилище **и возвращает клиенту** вместе с `resume_secret` |
| Возобновление (сервер) | `transport.rs` (WS: ~1085–1170; UDP: `handle_resume_packet` ~5754) | MAC по `resume_secret` от (session_id, client_nonce, addr); с некоторых пор привязка к `node_id` (`resume_node_matches`, `node_id_hex`); рабочий ключ = HKDF(`session_key`, client_nonce‖server_nonce) |
| Возобновление (клиент) | `connect_to_anchor_ws` (~4880–4990) | то же, берёт токен из `paired_anchors.json` |
| Кто пользуется | только Rust-узел в роли lite-клиента (`--anchor-url`); `set_session` вызывается лишь в тестах, `SESSION_ISSUE (0xC2)` обрабатывается в `transport.rs`. Телефонное приложение (`/mobile/ws`, TLS + токен устройства) этот механизм **не использует** (в Dart/Kotlin упоминаний нет) |
| Запасной путь | «классический» Hello (`HelloPacket`): подписанный Ed25519 приветствие с эфемерным X25519, `verify_peer_handshake_static`, защита от повторов `seen_hello_nonces` | уже есть и уже используется при отказе возобновления |

## 2. Угрозы и слабости (что подтверждено чтением кода)
1. **Рабочий материал на диске.** Кто прочитал `paired_clients.json`/`paired_anchors.json` (кража файла, резервная копия, чтение процессом), получает `session_key` и `resume_secret`: может возобновить сеанс от имени клиента (или якоря) и **расшифровать любые записанные ранее возобновлённые сеансы** — клиентские и серверные числа идут по сети открыто, а ключ вычисляется из сохранённого `session_key`.
2. **Нет прямой секретности** возобновлённых сеансов: рабочий ключ не содержит ничего эфемерного.
3. **Секрет возобновления — симметричный MAC-ключ**, общий у обеих сторон: компрометация любой стороны позволяет подделать и клиента, и ответ узла.
4. Привязка к identity уже частично есть (`resume_node_matches`, `node_id_hex`, подпись ответа `compute_resume_ack_mac`), но она держится на секрете из п. 1; повторы закрыты свежими значениями обеих сторон.
5. **Выгода механизма невелика:** он экономит один обмен рукопожатием. Для этого он хранит долговременный секрет, который нужно защищать, и ломает прямую секретность.

## 3. Рассмотренные варианты
- **A. Убрать возобновление по сохранённым секретам; восстанавливать соединение обычным подписанным Hello+ECDH.** Рабочие ключи каждый раз новые (эфемерный X25519 с подписью Ed25519 личности обеих сторон), прямая секретность, на диске нет ни рабочего ключа, ни симметричного секрета. Цена — одно лишнее рукопожатие при каждом переподключении (WS: порядка одного RTT).
- **B. Новое возобновление: PSK + эфемерный X25519 + HKDF с привязкой ко всему транскрипту (как `psk_dhe_ke` в TLS 1.3).** Сохраняет скорость, даёт прямую секретность, но оставляет на диске предварительно разделённый секрет (его кража = подделка клиента), добавляет новый протокол, который надо проверять заново.
- **C. Только заменить `session_key_hex` на вывод через HKDF от другого секрета.** Отвергнуто (как и требует план): секрет рядом с токеном, прямой секретности нет.

**Рекомендация: вариант A.** Он удаляет класс уязвимостей, а не прячет его, и использует рукопожатие, которое уже работает и уже защищено подписью, свежестью и защитой от повторов. Вариант B возвращаем, только если измерения покажут, что лишнее рукопожатие вредит (мобильные сети, большое число переподключений); тогда он проектируется как отдельный протокол с независимой проверкой.

## 4. Что становится с токеном сопряжения
- `SessionToken` теряет `resume_secret_hex` и `session_key_hex`. Остаётся **запись о праве**: `version`, `session_id`, `client_pubkey` (ключ подписи клиента), `node_id`, срок. Это не секрет: по ней нельзя ни расшифровать трафик, ни войти без закрытого ключа клиента.
- Вход клиента — подписанный Hello (самосертифицируемая личность). Если узел требует, чтобы подключались только сопряжённые клиенты, он сверяет `client_pubkey` из Hello с записями права (проверка в обработчике Hello, не в отдельном протоколе возобновления).
- `POST /pair/issue` перестаёт возвращать и хранить секреты: принимает `client_pubkey_hex`, возвращает `session_id` и срок.
- Сообщения `0xC0` (RESUME), `0xC1` (ACK), `0xC2` (SESSION_ISSUE) и их разбор удаляются из WS- и UDP-путей. Никаких скрытых запасных веток к старой схеме.

## 5. Миграция
- Явная версия формата хранилищ (`"version": 2`). Читатель: запись без `version` или со старым форматом **не принимается как токен**; при загрузке файл переписывается без секретных полей (затирание: запись нового файла, `fsync`, переименование), в журнал — понятное сообщение без значений.
- Старые токены недействительны; клиент выполняет сопряжение заново (QR/`--import-pairing`). Проект на ранней стадии, обратная совместимость с внешними версиями не требуется.
- `node_backup.rs`: копии `paired_*.json` уже не содержат секретов; уже сделанные резервные копии со старыми секретами остаются у владельца — в документе по копиям это указано, рекомендация удалить старые копии.
- Перед удалением кода составлен перечень всех точек использования (раздел 1); после правки `grep` по `resume_secret|session_key_hex|new_with_session_key|encode_resume|decode_resume|0xC0 RESUME` обязан вернуть только тест миграции.

## 6. Остаточные риски (честно)
- Узел, работающий без владельца, держит в памяти действующие рабочие ключи текущих сеансов и свой долговременный ключ личности (`~/.yandi_keys`, запечатан ключом устройства). Компрометация **работающей** машины открывает текущие сеансы — это не лечится на уровне протокола.
- Запись права (`client_pubkey`) раскрывает, какие ключи сопряжены с узлом (метаданные); хранится рядом с остальными данными узла, права 0600.
- Лишнее рукопожатие при каждом переподключении увеличивает задержку и число подписей; измеряется на реальных устройствах (раздел 8).

## 7. Тесты (автоматические)
1. Клиент A сопрягается, теряет соединение и поднимает новое: рабочий ключ новый, обмен идёт.
2. Клиент B с токеном/идентификатором A не принят: личность в Hello не совпадает с записью права.
3. Записанное приветствие (Hello) проигрывается повторно — отказ (`seen_hello_nonces`).
4. Изменены identity, `session_id` или nonce — отказ; состояние действующих ключей не изменилось.
5. Два соединения подряд дают независимые ключи (сравнение ключей двух сеансов).
6. Повреждённый/подделанный пакет не меняет действующие ключи.
7. Файл старого формата (с `resume_secret_hex`/`session_key_hex`) не принимается и **переписывается без секретов**; старое поле нельзя прочитать как новое.
8. Содержимое `paired_clients.json`, `paired_anchors.json` и их копий не содержит ни 64-hex рабочего ключа, ни секрета возобновления (проверка по маске и по известным значениям).
9. Нет в коде обработчиков `0xC0/0xC1/0xC2` (тест-страж по исходникам).
10. Сценарий кражи файлов состояния: имея только файлы, нельзя ни расшифровать записанный трафик, ни подключиться (нужен закрытый ключ клиента).

## 8. Испытания на реальных процессах и устройствах (планируются, пока **не проведены**)
Два/три/четыре узла на `testnet`; обрыв и возврат соединения; смена IP/интерфейса клиента; параллельные соединения; передача сообщений и файлов во время переподключения; перезапуск одного узла посреди обмена; измерение времени переподключения до и после. Протокол испытаний с версиями, коммитами, командами и результатами — отдельным файлом; не проведённое будет помечено «не проводилось».
