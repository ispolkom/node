# План рефакторинга: малое ядро-супервизор и изолированные модули

Статус: **версия 3 — решение принято: делаем только малое подмножество, остальное откладываем до реальной потребности.** Текущая версия проекта опубликована (`main`), откат к ней всегда возможен; любой шаг должен оставлять проект рабочим и проверяемым.

## Решение (после обсуждения с независимым рецензентом)

Полный рефакторинг сейчас дал бы отрицательную отдачу: сеть крошечная (один живой публичный узел), а пользователи ощутят совсем другое (запасной путь по TCP, сквозное шифрование через ретрансляторы, мобильное приложение, скорость). Поэтому:

**Делаем сейчас (дни, не недели):**
1. ✅ **Присмотр за долгоживущими задачами** — `src/supervisor.rs`: имя, политика (`Log` / `Restart` с лимитом перезапусков / `Fatal`), причина завершения (паника, неожиданный возврат), состояние на `GET /api/kernel/status`. Под присмотр переведены 11 важных циклов; оценка пользы — после следующих 5–10 (условие остановки: если польза не видна, не расширять).
2. ✅ **Дисциплина запусков:** `scripts/check_spawn.sh` не даёт числу «голых» `tokio::spawn` расти (CI и `scripts/check.sh`).
3. ✅ **Тесты отказов:** паника, неожиданный возврат, «падает слишком часто», критичная задача (`src/supervisor.rs`).
4. **Изоляция процессами только по реально рискованным границам** — когда будет удобно, не как условие для продуктовой работы: сначала декодеры (звук `opus`, картинки `image`), затем рабочий выхода, если граница остаётся простой.

**Порядок работ:** тихая смерть задач (сделано) → запасной путь по TCP/TLS → сквозное шифрование через ретрансляторы → изоляция декодеров → пересмотр архитектуры.

**Откладываем до триггеров** (несколько пользователей, эксплуатационные инциденты, достаточное число независимо перезапускаемых частей):
шина управляющих сообщений; дескрипторы с поколениями; общий модульный каркас; квоты по модулям; агент ключей; единица systemd на модуль; несколько узлов в одном процессе как архитектурная цель; массовое устранение глобальных переменных сверх того, что выпадает само при правках.

Ниже — полный план как **справочник** на случай, когда триггеры наступят.

## Зачем

Сейчас узел — один процесс, где `main.rs` (≈1200 строк) вручную запускает фоновые задачи (в коде 134 вызова `tokio::spawn`) и держит глобальные состояния (28 мест с `OnceLock`/`static`). Из этого следуют реальные проблемы:

1. **Тихая смерть задач.** Паника внутри `tokio::spawn` убивает только эту задачу, и никто этого не замечает: например, умерла рассылка карточек, а узел «работает». Нет ни перезапуска, ни сигнала. Так же молча может закончиться задача с обычным возвратом — это тоже событие.
2. **Нет учёта по частям.** Нельзя сказать, сколько соединений, очередей и байт у прокси, звонков, чата, связи с узлами, и нечем их ограничить.
3. **Одна общая зона риска.** Разбор чужих пакетов, выход в интернет, декодирование звука (C-библиотека `opus`) и картинок профиля (крейт `image`), веб-страница и ключи живут в одном адресном пространстве: ошибка в любом из них задевает всё остальное, в том числе ключи.
4. **Глобальные синглтоны** мешают изоляции и мешают запускать несколько узлов в одном процессе для тестов.

## Принципы

1. **Ядро маленькое и скучное.** Только запуск, остановка, наблюдение, перезапуск, учёт, лимиты. Оно **не разбирает чужие данные** и не содержит логики сети. Цель — маленькое ядро в духе OTP, а не «фреймворк микросервисов внутри одного бинарника».
2. **Ядро управляет, но не гонит трафик.** Плоскость данных остаётся внутри модуля, который владеет сокетом. Ни пакеты, ни кадры звука и видео, ни байты SOCKS, ни куски цепочек не идут через шину.
3. **Поведение не меняется.** Протокол и формат на проводе не трогаем. Замок: модульные и сетевые тесты остаются зелёными на каждом шаге.
4. **Каждый шаг обратим и проверяем командой.**
5. **Изоляция — по границе недоверенного разбора**, а не по названиям модулей. Сначала дешёвая изоляция внутри процесса, процессы — только там, где они реально снижают риск.
6. **Один логический контракт, но не одна иллюзия.** Модуль внутри процесса и модуль в другом процессе имеют одинаковую логику жизненного цикла (запуск, готовность, здоровье, остановка, перезапуск), но не скрываем, что IPC — это не вызов функции: другие ошибки, другая задержка, обратное давление и возможность зависнуть, а не умереть.
7. **Честные числа.** Показываем только то, что можем измерить правдиво. Точный процессор и память на модуль внутри общего процесса получить нельзя — обещаем их только после процессной изоляции.

## Решения, принятые до заморозки интерфейса

Сначала фиксируем семантику, а не имена методов:

| Вопрос | Решение |
|---|---|
| Кто владеет задачами | **Ядро** через набор задач модуля (`JoinSet` + токен отмены). Голых `tokio::spawn` внутри модулей нет: каждая долгоживущая задача зарегистрирована. |
| Что считается событием | падение (паника) **и** неожиданное завершение; причина записывается |
| Остановка | токен отмены → срок на мягкую остановку → принудительное прекращение |
| Кто владеет сокетами | модуль, в котором данные; ядро сокетов не держит |
| Состояния | `starting → ready → degraded → failed → stopped`; «жив» и «готов» — разные вещи |
| Перезапуск | политика на модуль: *перезапускать* / *критичный (падение = выход узла под присмотр systemd)* / *не перезапускать*; **интенсивность**: не более N перезапусков за T секунд, дальше — `failed` и эскалация |
| Что после перезапуска | модуль объявляет, что хранит и что теряет; доступ других модулей — через **дескрипторы с номером поколения**, устаревший дескриптор возвращает понятную ошибку, а не висит |
| Зависимости запуска | явный граф зависимостей модулей; стратегия «один за одного» по умолчанию, «все вместе» — только для логически связанных |
| Обратное давление | все очереди ограничены; поведение при переполнении задано в контракте |
| Сроки | у каждого вызова между модулями есть срок |
| Что фатально для узла | нарушение инвариантов шифрования, повреждение ключей, потеря критичного модуля связи |
| Версионирование IPC | версия протокола в каждом кадре с первого дня |
| События / запросы | **события** (карточка проверена, адрес изменился, пул выходов обновлён) — шина; **запросы и команды** (выбрать выход, найти узел, подписать) — типизированные дескрипторы с ограниченными вызовами. «Всё через шину» запрещено. |
| Паники | основной процесс — `panic = unwind`; паника перехватывается на границе задачи модуля, с трассой в журнале. Изолированные рабочие процессы позже могут быть `abort`: сам процесс — граница отказа. |
| Среда выполнения | один `tokio` на процесс; отдельный планировщик нужен только как довод за отдельный процесс |
| Ключи | долговременный ключ личности — в отдельном агенте (когда дойдём): операции только `sign_identity` и закреплённые узкие операции; сеансовое шифрование с эфемерными ключами остаётся рядом с плоскостью данных. Долговременный ключ не подписывает каждый пакет и не должен. |

## Шаги

### R0. Замок поведения (S)
- Зафиксировать базу: список модульных и сетевых тестов, время и результат (`scripts/check.sh полностью`).
- Тест «тихая смерть»: уронить фоновую задачу и показать, что сейчас об этом никто не узнаёт (красный тест, который R1 сделает зелёным).
- **Готово, когда:** база записана, тест «тихая смерть» воспроизводится.

### R1. Супервизор и владение задачами (M)
- Интерфейс модуля по таблице выше; ядро: запуск, наблюдение, перезапуск с отступом **и интенсивностью**, `ready/alive/degraded`, токен отмены, срок остановки.
- Обернуть существующие фоновые циклы как модули без изменения их логики: рассылка карточек, проверка достижимости, ретрансляция и записи доступности, обновление bootstrap, очистка цепочек, проверка стран выходов, сброс учёта байт, TLS-вход.
- **Состояние переносится во владельцев по мере оборачивания** (а не отдельным большим этапом): оборачивая модуль, мы решаем, кто владеет его глобальным состоянием, и переводим его на дескриптор.
- `GET /api/kernel/status` (JSON): модули, состояние, число перезапусков, причина последнего завершения.
- **Готово, когда:** тест «тихая смерть» зелёный (упавший модуль поднимается сам, остальные не затронуты; модуль, падающий слишком часто, переходит в `failed`), прежние тесты зелёные.

### R1.5. Структурные журналы и точки отказа (S)
- Точки отказа для тестов (включаются только в тестовой сборке): паника после N событий, зависание после N событий, задержка каждой операции, потеря следующего сообщения, заполнение очереди, выход процесса с кодом, игнорирование остановки; сценарии повторяемы по зерну.
- Структурные журналы по модулям.
- **Готово, когда:** каждый сценарий отказа воспроизводится командой и ловится тестом.

### R3. Владение без глобальных переменных (M, остаток после R1)
- Довести перенос состояния во владельцев для оставшихся мест: каталог карточек, записи доступности, учёт байт, секрет устройств, пул выходов, цепочки.
- Следствие: несколько узлов в одном процессе (быстрые тесты), ясные границы.
- **Готово, когда:** в `src/` нет изменяемого глобального состояния вне ядра и тестового кода (проверка скриптом), тесты зелёные.

### R4. Типизированные управляющие контракты (M)
- События — шина с ограниченными очередями; запросы и команды — типизированные дескрипторы со сроками.
- **Готово, когда:** модули общаются только через эти два механизма; убийство одного не вешает остальных (тест на точках отказа).

### R2. Логические квоты и метрики (M)
- Точные логические счётчики по модулям: соединения, очереди и их глубина, байты, число задач, задержка цикла событий. Оценки памяти — только там, где она инструментирована.
- Квоты и мягкая остановка при превышении; метрики в `/api/kernel/status` и журналах. Красивая страница нагрузки — позже.
- Жёсткий учёт процессора и памяти — только после процессной изоляции и `cgroups`.
- **Готово, когда:** модуль, превысивший квоту, ограничивается, не задевая соседей (тест).

### R5. Изоляция процессами (L, Linux сначала)
Порядок по границе недоверенного разбора:
1. **Декодеры:** звук (C-библиотека `opus`) и картинки профиля (`image`) — сложные чужие форматы.
2. **Рабочий выхода:** внешняя сеть, DNS, злоупотребления; ключей не держит. (Если по замеру декодеры окажутся безопасными, этот пункт может стать первым.)
3. **Веб-страница и API:** разбор HTTP, загрузки.
4. **Агент ключей:** после того как разделены долговременная личность и сеансовый материал.
5. **Разбор входящих пакетов основной связи:** последним, только после измерений скорости.
- Межпроцессный протокол: сокеты Unix, кадры с длиной, версия, ограничения размера, сроки, готовность/здоровье; проверка зависания, а не только смерти.
- Усиление: отдельные пользователи, `no_new_privs`, `seccomp`, `cgroups` (юниты systemd).
- Режим «всё в одном процессе» остаётся для Windows, macOS и телефона.
- **Готово, когда:** настоящий `SIGKILL` рабочему процессу и его зависание не задевают остальное и ключи; ядро не растёт по памяти.

### R6. Упаковка и эксплуатация (M)
- Юниты systemd на модули (только когда есть реальные рабочие процессы), проверка состояния, журнал по модулям, документация эксплуатации.

## Чего не делаем

- Не пускаем данные через ядро или шину.
- Не переписываем транспорт и протокол; формат на проводе не меняется.
- Не обещаем точный процессор и память на модуль внутри одного процесса.
- Не вводим микросервисы «ради красоты»: процесс — только там, где он снижает риск.
- Не называем ядро «непадающим»: оно маленькое и простое, а его падение — отдельный сценарий (запуск под systemd, быстрый старт).
